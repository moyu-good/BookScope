# ADR-010：章脉共享索引 —— 整本读一次,全书功能从它派生

## Status

**已批准 · 2026-06-23 作者签字"签" · 实现按迁移计划启动**

- 代际：r2-agent-loop **之上的结构层重构，不另起代际**（章脉是结构索引层，不改 r2 agent loop / r2 协议；作者可后续升 r3，本 ADR 不擅自宣布代际升级）
- 起草：副管理
- 创建日期：2026-06-23
- 作者签字：**2026-06-23 "签"**（D-3 probe 跑完、数据定案分维后签字）
- NORTH_STAR 措辞：**不改**——按 D-6 论证，章脉不比现状更违反"拒绝批量预处理"（它只让本就批量的全书功能共享一次、且每字段带证据，agent loop 照旧 live）。作者签字未要求改措辞，故保持原文不动。
- 决策摘要：把十来个"全书结构类"功能各自独立跑一遍整本 map-reduce，改成**整本只精读一次、出一份带原文证据的逐章结构（章脉），各功能从章脉派生自己的视图**。几百万字书的全书分析从 ~750 次 LLM 调用降到 ~75 次 + 若干便宜视图，原文 input 只发一遍而非十遍，重开书全功能秒出。

## Context / 背景

2026-06-23 作者点破：几百万字的书（如网文）不是边角的"极端"场景，是**核心场景**——作者本人的网文草稿就是几十万到几百万字。这种书的全书分析当前跑不动，必须用架构转向来解，不是加个提醒条就完事（提醒条已落地 commit `69a38e9`，是安全网不是答案）。

当前全书结构类功能（关系图 / 关系演变 / 叙事流 / 人物弧线 / 叙事曲线 / 节奏 / 伏笔回收 / 支线编织 / 时间线 / 论点结构，约 10 个）走 1.4 穷尽化：每个功能各自 `generate_X_exhaustive(chunks)`，按字符预算（`DEFAULT_CHAR_BUDGET=40000`）把整本切段，每段一次 LLM 调用抽本段逐章结构，再合并。

实测触发点：《亏成首富从游戏开始》（epub 11.9MB、702+ 章，约 300 万字）跑叙事曲线穷尽化，反复"主解析失败，从截断输出抢救到 11 章"，只抽到零头。

CLAUDE.md 硬约束在设计阶段就要 lock：原文证据是立身之本（没证据不输出）；BYOK + 普通 CPU 可跑、不引 GPU；provider-agnostic。

## Problem / 问题

### 问题 1：截断 —— 分段按"输入字数"切，卡死的却是"输出 token"

所有穷尽化功能 `max_tokens=8000`，分段按输入字数（40000 字/段）。但真正撑爆的是**输出**：输出量 ∝ 段里章数 × 每章带证据的结构，跟输入字数不成正比。

网文章节短（2-3 千字/章），一个 40000 字的段里塞进 15-20 章 → 每章一条带 evidence 的结构 → 输出顶爆 8000（flash 还要分一部分给 reasoning_content，见 memory `reference_reasoning_model_token_budget`）→ 截断。**越是短章密集的书越容易爆，而短章密集正是网文、正是作者的核心场景。** 这是设计错位：段大小该由输出预算定（限每段章数），现在由输入字数定。

### 问题 2：慢和贵 —— 每个功能各跑一遍全书，互不共享

十来个全书功能，每个独立把整本 map-reduce 一遍。300 万字 → 每功能 75 段 = 75 次调用，十功能 ≈ **750 次**。更要命：同一段 40000 字原文被当 input **重发十遍**（每功能 prompt 不同 → 缓存键不同 → 缓存救不了跨功能重复，也救不了首跑）。

按 memory `reference_deepseek_cost_model`，成本 93% 在 cache miss 的 input。这里就是把同样的 input 付了十遍。而且每段都在重新判"谁在场 / 发生了什么"这些**跨功能高度重叠**的底层事实。

### 问题 3：没有共享的结构层

上传时建的 `assembler._kg`（MinimalKGExtractor，canonical 人物）只有实体清单，不带逐章的事件/张力/关系/伏笔这些功能要的结构。所以每个功能只能从原文重抽。缺的是一层"读过一遍、带证据、可被所有视图查询"的逐章结构。

## 方法论锚

- **CQRS / 物化视图（materialized view）+ 单一事实源**：一份权威的写模型（章脉），多个便宜的读投影（各功能视图）。经典数据工程做法——重的抽取算一次、物化、查询便宜。
- **作者自己 6/12 定的两条 usecase（与外部思想家同级，优先用）**：`reference_deepseek_cost_model` 的"深读钉稳定上下文，越问越省"+ `project_retrieval_direction` 的"优先 probe 长上下文+缓存，冲 ≥90% 命中率"。**章脉就是那个"钉稳定的上下文"**——一次读进结构、缓存、所有功能复用。这个转向不是新发明，是把作者已定方向落到结构抽取上。

## Decision / 决策（草案，待审）

### D-1：章脉 = 整本一次精读出的、带证据的逐章结构，是全书功能的单一事实源

整本只跑一次 map-reduce，抽出逐章结构记录（章脉），缓存成这本书的结构索引。各全书功能不再各跑全书，改从章脉派生视图。

### D-2：章脉每章记录字段（各字段带 evidence）

一条章脉记录是各全书功能所需字段的并集，每个有结论的字段都钉原文片段 + 真章号（复用现有 `verify_citations` 章号纠偏，见 commit `b48625b`）：

| 字段 | 服务的功能 |
|------|-----------|
| 在场人物 present[] | 叙事流 / 关系图 |
| 关键事件 events[] | 时间线 / 节奏 |
| 张力 tension / 情感 sentiment / 视角 pov / 主支线 | 叙事曲线 / 节奏 |
| 触及的关系对 relations[]（对 + 强度 + 转折候选）| 关系图 / 关系演变 |
| 伏笔候选 foreshadow[]（埋/收 + 钩子）| 伏笔回收 |
| 支线标签 subplot_tags[] | 支线编织 |
| 人物处境 char_states[] | 人物弧线 |
| 主张 claims[]（理论书）| 论点结构 |
| evidence 片段（每个有结论的字段挂）| 立身之本：没证据不进章脉 |

**题材自适应**：小说重 伏笔/关系/人物弧；理论书重 claims/概念；诗歌重 母题/意象。章脉 schema 是超集，按 ingest 时判定的题材只抽相关维度（不强抽诗歌的"伏笔回收"）。

**证据粒度(2026-06-23 实现中发现,牵动立身之本,待裁)**：章脉每章带一条 chapter 级 evidence（够做章号纠偏 + 章级锚）。但关系图边 / 叙事流 pairs / 时间线事件这些视图历来是**每条带逐字证据**（NORTH_STAR：每条边钉原文）。给章脉里每条 relation/event 都加 evidence 会让抽取输出暴涨——人物维 12 章已 5419 token，加逐条证据要把 D-7 章闸砍半、spine build 翻倍贵。三条出路:
- **A 每条加证据**:满精度,但 spine build 成本翻倍(章闸砍半)。
- **B 章级锚 + 按需取证**:章脉只记"这条关系/事件在第几章(钉到 chunk)",用户点开某条边时一次便宜调用/检索取那一句精确原文——更贴 NORTH_STAR 的"查询时证据现场取"。
- **C 不迁这几个**:关系图/叙事流/时间线继续走各自现有 exhaustive(句级证据),只迁章级标量视图(叙事曲线/节奏)。
- **现状(2026-06-23 第 3 步起步)**:先按 C **不降级**——已迁叙事曲线/节奏(满精度派生),关系图/叙事流/时间线挂起。但 C 下迁移省不下钱(章脉只服务 2 个视图≈各跑成本),**迁移见效要 A 或 B**——这条归作者裁。倾向 B(NORTH_STAR 对味 + 不翻倍成本)。

### D-3（核心待审）：章脉怎么抽 —— 输出预算切段 + 分维抽取

两个子决策，都是真问题：

**(a) 按输出预算切段，不按输入字数**（同时修问题 1 的截断）。段大小由"每段最多多少章"定（短章书一段少塞几章），保证每段输出落在 max_tokens 内。或：动态切——估每章输出 token，累加到接近预算就断段。这条**独立于大转向也该做**，见 D-7。

**(b) 一次抽全维 vs 分维多趟 —— probe 已定案：分维。**

2026-06-23 probe(`scripts/probe_chapter_spine.py`，靶子《亏成首富》短章网文前 4 段，flash，max_tokens=8000）：

| | 全维一趟 | 人物维(分维) | 情节维(分维) |
|---|---|---|---|
| 截断率 finish=length | **3/4 段爆** | 0/4 | 0/4 |
| 爆段后果 | 输出顶满 8000、JSON 截断**一章都没解析出来** | — | — |
| 覆盖(总抽出章) | 16(只 1 段没爆) | — | 65(4 段全解析,16-17 章/段) |
| 质量(没爆那段张力 vs 情节维) | 均差 1.0(0-10 标度) | — | 参照 |

结论:**全维一趟在短章网文上 3/4 直接爆、爆了一章都救不回来,否决。定方案 ②分维多趟**（小说:人物维 + 情节维 2 趟;理论书加概念维）。

**额外发现(强化 D-7)**:就算分维,情节维一段 17 章已吃到 5759/8000 token,离顶不远——段再密一点分维也会爆。所以 D-7「按输出预算切段」不是可选,是分维之外**还必须做的硬前提**。另:这本检出 1676 章、147 段,章脉 build 本身不便宜(147×趟数),但一次 + 缓存,仍远胜十功能各跑。

### D-4：各功能视图怎么从章脉派生

分两类：
- **纯计算视图（0 次 LLM）**：叙事曲线（tension/sentiment/pov 已在章脉）、节奏、叙事流（present[] + relations）、关系图（relations[] 聚合）。章脉建好后这些**免费**、秒出。
- **轻 LLM 视图（章脉很小，1 次小调用）**：论点结构。
- **不迁、留各自路径（2026-06-23 实现中更正）**：
  - **时间线**:命根子是把倒叙/多线**还原成真实时间先后**(temporal reasoning),章脉的逐章 events 是**阅读顺序**——naive 派生会把"还原倒叙"这个核心价值弄丢。需章脉之外的时序推理,留 `generate_timeline_exhaustive`。
  - **伏笔回收**:跨章把埋点配对收点要 setup→payoff 推理,章脉的 foreshadow 候选只是逐章标记、没配对。留各自路径(也呼应 D-2 里伏笔本就特殊)。
  - 教训:不是所有"全书结构"功能都能从逐章章脉 naive 派生——**只有"逐章独立可填"的维度(张力/在场/关系)能;需要跨章/跨时序推理的(时序还原/伏笔配对)不能**。章脉省的是"重复读全书"那部分,省不掉"专门的跨章推理"。

### D-5：章脉的缓存与持久化（接 ADR-008 L3）

章脉是书级、一次建成、书不变就不变 → 天然适合缓存。进程内 LRU + 磁盘双层，key = `book_id + 章脉schema版本 + 抽取prompt版本`。重开书直接 mmap 加载，全功能秒出。这正是 ADR-008 L3 book 预热缓存的延伸：L3 之前缓存 vector index + KG，现在加章脉。

### D-6（关键）：与 NORTH_STAR "拒绝批量预处理" 的关系 —— 必须作者裁定

NORTH_STAR 立的是："拒绝批量预处理+静态展示的旧范式；所有结论由查询时 agent 循环根据原文证据现场生成。"章脉是一次批量预读，表面踩线。诚实说清区别：

- **r0 旧范式**：预算好结论/分数、不带证据、静态展示、agent 不推理。
- **章脉**：(1) 每个字段带原文证据，没证据不进章脉——立身之本不破；(2) 全书结构类功能**今天就已经是批量 map-reduce**，不是 live agent loop——章脉只是让这十个已有的批量 pass **共享一次**，而不是各跑一遍，没有把"现场推理"退化成"预处理"，只是把已有的重复批量活去重；(3) 查询时 agent loop 功能（问书 / 编排 / 前情回顾）**照旧全程 live**，一个字不改。

所以严格说，章脉不比现状更违反 NORTH_STAR——它优化的是本来就批量的那部分。但"整本预读建索引"是范式措辞上的转向，**这条线归作者裁定**，是本 ADR 签字的核心。

### D-7：问题 1（截断）可独立先修，不等大转向

D-3(a) 的输出预算切段，跟章脉转向解耦——现在就能改现有 `_internal/exhaustive.py` 的分段逻辑，让短章网文不截断。建议作为本 ADR 签字前的"无悔动作"先落（不改架构、只改分段维度）。

## 账（成本/调用对比）

| | 现状（每功能各跑全书）| 章脉（3 趟建 + 派生）|
|---|---|---|
| 300 万字书全功能 LLM 调用 | ~750 次 | ~225 次（建）+ 少量视图调用 |
| 原文 input 发送 | ~10 遍 | ~3 遍（分维趟数）|
| 重开同书 | 各功能各自重跑/部分命中 | 章脉缓存命中，全功能秒出 |

## Consequences / 后果

### 好
- 几百万字书全书分析从跑不动变跑得动；调用数 / input 成本 ~3x 降；重开书秒出。
- 对齐作者已定的 ≥90% 缓存 + 深读钉稳定上下文方向。
- 截断根因修掉，短章网文（核心场景）不再只抽到零头。

### 弊
- 章脉 schema 是全功能字段并集，加新功能可能要扩 schema + 重建章脉。
- 一次抽全维（若选方案①）单段输出压力大；分维多趟（方案②）实现更复杂。
- 章脉抽取本身的质量是所有视图的天花板——章脉抽错，所有派生视图一起错（单点）。要保留"某功能可绕过章脉直接重抽"的逃生口做对照。
- 范式措辞上的代际转向，要 case-study 记清"为什么这不违反证据立身"。

### 撤回条件
- 一次抽全维质量明显低于现状各功能专抽（probe 实测降质 → 退回分维或退回现状）。
- 章脉单点错导致多视图连锁错、且难定位。
- 派生视图发现章脉字段不够、频繁要回原文重抽 → 章脉没省下事。

## Alternatives / 备选方案

- **A-1 只修截断、不上章脉**：小、即时、不动架构；但慢和贵（每功能各跑全书）还在。= 本 ADR 的 D-7 单独做。作者若只想先止血可选这条。
- **A-2 边读边分析（只分析读过的范围）+ 流式出部分结果**：对齐读书优先 IA，把成本 bound 在读过的章；但伏笔回收这类要全书的功能做不全。可作章脉的补充策略，不替代。
- **A-3 加大 max_tokens / 缩小段**：治标。段越小段越多（调用更多更贵），max_tokens 越大单调用越贵且 provider 有上限。不解决跨功能重复。
