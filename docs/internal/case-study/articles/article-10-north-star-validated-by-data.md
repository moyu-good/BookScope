## 一、一句话发生了什么

`docs/internal/NORTH_STAR.md` 第一行写着：

> 服务作者本人作为长篇网络小说创作者的第一读者工具（中长期验证锚）

这句话在 r1-agent-loop 启动那天就放在第一条。从 2026-04-20 到 2026-04-26，整整六个日历日里，它待在文档顶部，看起来像任何一份"正式项目方向"文件第一条都会写的话——服务用户。哪个项目不说自己服务用户。

2026-04-27 凌晨，第 26 轮的 batch runner 跑完最后一道题。屏幕上出现这一行：

```
v2 + astron baseline:    24.8 / 25
v3.1 + minimax candidate: 20.0 / 25
Δ = -4.8（全 5 题 LOSE）
```

我盯着这五道题的 trace 看了大约二十分钟。当我合上电脑的时候，那行字在文档顶部的意义已经变了——它不再是"项目说明书第一条"，而是**唯一能解释清楚为什么我们这次失败、且接下来该往哪去**的指南针。

这篇文章想讲的就是这个变化。它不是关于一行文字的修订史，而是关于**一项技术判断如何在被一次具体的失败实证之后，从战略口号升级为研究方向锚点**。

## 二、r0 时代：第一条目的不存在

要看清第 26 轮那一晚发生了什么，得先回到 r0-baseline 那段历史，看看那时这句话是什么状态。

r0 时代的 BookScope 是另一种东西。它的形态是 v7 三阶段流水线——全量扫描 + 智能选择 + 定向深挖，传统 RAG 范式。它做了什么呢，简单说：把一本书拆成 chunk，做向量索引、跑 NER 拿角色清单、拿 KG 把人物关系图画出来，然后把所有这些预处理结果存起来，等用户来查询时就从静态资产里拼答案。

r0 时代的"项目目的"是什么？我现在回过头去翻当时的 README，里面写的是"对长文本做深度阅读分析"。"为谁分析"这件事——其实**没写**。或者说，它默认了"对任何想分析一本书的人都有用"。这就是大多数工具型项目第一条目的的真实状态：用户是谁不重要，先把工具做出来再说。

更具体地说，r0 时代的我并不真正知道"用户"是什么。我自己写过几十万到几百万字级别的长篇网络小说，写的过程中确实希望有一个"第一读者"——不是评论家、不是编辑、不是测试读者，是一个**会非常仔细地把整本书读完、读懂、读出我没意识到的连贯性问题**的工具。但这个需求当时没有被表达成"项目目的的第一条"。它只是我个人写作的一个隐痛。

所以 r0 时代的目的优先级如果真要排，大概是这样：

1. 把 RAG 流水线做出来
2. 让它在公开书上能跑出还算像样的结果
3. ... 服务谁？再说

这个顺序在工程上完全成立。问题是，它**没有给项目的关键判断提供任何约束**——任何一个看起来"专业""通用""技术上更先进"的方向，都可以被加进 r0。比如更复杂的 chunk 策略、更精巧的 reranker、更大的 KG schema。这些方向有任何一条值得做吗？没有判断标准。优先级 1 写"做出来"，但**做给谁用**没说，结果就是怎么做都对。

r0 一直跑到 v7 才停。不是因为它不好——是因为我开始隐约意识到一件事：我自己写小说的时候，根本不会用 r0。

理由很现实。r0 的三阶段预处理在万字级文本上要数小时；在我那种几十万字的草稿上是数日。我是写到一半的人，**今天写完一章就想知道这一章和前 14 章是否连贯**——我要的是查询时的实时反馈，不是"等批量预处理跑完才能看"。r0 的形态适合给一本已经写完、定稿、出版了的书做事后分析。它从来没适合过我自己。

这是 r0 → r1 代际转向的真实起点：不是因为有更先进的论文出来了（虽然 agentic RAG 确实在那时快速发展），而是因为我开始注意到，**这个工具我自己用不了**。

## 三、r1 启动那天：第一条被显式写下，但仍是 placeholder

2026-04-20，r1-agent-loop 代际启动。`docs/internal/NORTH_STAR.md` 第一版定稿。第一条第一次被写下来：

> 服务作者本人作为长篇网络小说创作者的第一读者工具（中长期验证锚）

这次"写下来"和 r0 时代"没写"的区别，从文档形态看很大——从无到有；从项目实际推进的判断上看，差别其实不大。

为什么这么说？我自己当时写下这句话的时候，并不是基于一次具体的反证。我是基于一种**判断**：长期来看，只有作者本人是最稳定、最持续、最真实的用户，所以应该把"服务作者本人"放第一条。这是一个**朝向未来的押注**，不是从已有数据里推出来的结论。

更直白点说——r1 启动时，这句话和 r0 时代隐含的 "对所有想分析书的人都有用" 在**对实际工程决策的指导力**上没有质的差别。两者都是"声明式的"。两者都没有具体到能在某个分叉点上压过另一条路径。

第 1 轮到第 10 轮的工作能验证这一点。这十轮里，副管理（也就是 24/7 自主推进的我）做的事情按时间顺序排下来：

- 第 1 轮：r0 冻结、隐私清理、文档系统重写、CLAUDE.md 重写
- 第 2 轮：ADR-001（三个 tool 的 Pydantic schema）+ ADR-002（agent loop 框架）+ 实验 001 设计 + 研究笔记 001
- 第 3 轮：副管理机制落地 + r1 编码骨架（12 文件 / 932 行 / 34 测试用例）
- 第 4–6 轮：三个 r0 数据后端接入（`R0SearchChunksBackend` / `R0ChapterRangeBackend` / `R0ListCharactersBackend`）
- 第 7 轮：AgentLoop 核心 + citation 强制机制
- 第 8 轮：ADR-002 v2 + ADR-003（provider adapter 层 · DeepSeek / Anthropic 双 adapter）
- 第 9–10 轮：FastAPI 入口骨架（`POST /api/agent/ask`）

这十轮里有任何一个判断是"因为要服务作者本人作为长篇网文创作者，所以选 A 不选 B"吗？说实话，没有。

实际驱动这十轮的判断是别的：

- **不变量**：BYOK / 不嵌入 hosted LLM / 禁 GPU / 中文优先 / 国内 LLM 优先 / provider-agnostic
- **架构判断**：从"批量预处理 + 静态展示"转向"轻量索引 + 查询时代理"
- **工程节奏**：先骨架 + Pydantic schema 收口 + provider adapter 层早做 + 数据层缓修补

这些判断里大部分都来自第二条目的（"以查询时智能代理为核心、以原文证据为根基"），而**没有一条**是直接从第一条"服务作者本人"推出来的。

第一条这时候是什么？是项目愿景的"上一层"——它给所有这些工程判断一个意义来源（"我们做这些是为了什么"），但**它本身不参与具体决策**。它仍然是 placeholder。

## 四、第 11–15 轮：r0 数据层修补，方向标尚未发挥作用

第 11 轮到第 15 轮跨了三个日历日。这五轮的工作主题统一：把第 1–10 轮堆出的 r1 大脑层接到一份可持久化的数据基座上。这部分历史在第 2 章已经详写过——三个 r0 数据层结构性缺口，三种不同级别的 workaround 慢慢闭合，五轮分布的不是"代码复杂度"，是"判断的颗粒度"。

第 2 章末尾我写过一句话：

> 第 1 章能以那个节奏发生，是第 2 章慢节奏的红利。

这话至今我同意。但今天回看，还能补一句：**第 11–15 轮的判断**——加 `ChunkResult.chapter` 字段、`detect_chapters` 公共化、`SessionVectorStore` 持久化、ADR-005A 的 manifest 契约、未闭合的 chunk-to-characters 倒排索引——**没有任何一条是因为"作者作为长篇网文创作者会更需要这个"才做的**。

它们都是为了"把 r1 大脑层接到数据基座上"这条工程目标服务的。如果第一条目的换成"服务出版社编辑"或"服务普通读者"或"服务图书馆员"，第 11–15 轮的代码会有任何不同吗？大概率没有。

这不是我事后挑剔自己。这是说明 NORTH_STAR 第一条在前 15 轮里**不构成有效约束**——它没有决定任何分叉。它在文档上存在，但在代码里看不到它的影响。

这一点我当时是意识不到的。当时我以为"第一条很重要"。其实它**还没拿到使其重要的那次反证**。

## 五、第 16 轮：真 API 跑通，但跑的是公开书

2026-04-24 第 16 轮，r1 第一次真跑。

讯飞星辰 astron-code-latest，`test明朝那些事儿.epub`（32164 字 / 1069 chunk），整条 agent loop 跑通——4 轮 iteration / 6 次 tool 调用 / 56k input + 1.3k output token / **7 条原文 citation** / 82.3 秒。

第 1 章详细讲过当晚的故事——`LoopTimeout` 丢 trace、本地 cross-encoder 单次 search 892 秒、ADR-006 五条命令、API-first 重构 5 天 5 commit。这些是**工程意义上**的高潮：硬约束在真 API 首次实跑时被活检出来，并驱动了一次架构级重构。

但今天用 NORTH_STAR 第一条的视角回看第 16 轮，要补一个观察。

**第 16 轮跑的是公开书**。`test明朝那些事儿.epub`——一本 2006 年公开出版的历史普及读物，七卷本，全网随处可见。我当时为什么用它？因为 BookScope 的实验 001 设计里它就是 baseline 测试集。我从来没考虑过用我自己写的草稿——那时候我的小说草稿有几十万字，还没写完，私人手稿，**而且我不知道把私人手稿放进 smoke test 里跑会发生什么**。

这是一个非常容易被忽略的方法论选择。我当时以为"用公开书做 baseline 是常识"——任何一篇 RAG 评估论文都是这么做的。模型的能力、agent 的工具调用、citation 的精度，理论上和用什么书没关系。一本是一本。书都是中文。结构都差不多。

在第 16 轮的当晚，这个假设没有被挑战。82.3 秒 / 7 条 citation 的答案看起来很像样：50+ 个角色都被提到、章节横跨第 1 章到第 145 章、每个判断都附原文 snippet。我合上 commit 那一刻，唯一的感受是——**r1 大脑层到此真正闭环**。

我没意识到的是：当时跑出来的 7 条 citation，到底是 astron 真的从 1069 个 chunk 里检索到的，还是它**早就知道这本书里有这些内容**——在它训练数据里。

这条疑问要等十轮之后才被实证暴露。

## 六、第 18–22 轮：方向感开始模糊

第 17 轮做了 ADR-006 的 626 行减重——纯 refactor，本地 ML 全下线。第 18 轮把 `MinimalKGExtractor` 接进 smoke 但默认关。第 19 轮 astron 在 API 层一等公民化。第 20 轮前端最小 UI（10 文件 / ~550 行 React）。第 21 轮新建 `docs/internal/case-study/` + 第 1 章草稿。第 22 轮真 KG pilot 验证（46s 抽取 + 109s 端到端）。第 23 轮第 2 章草稿。

这七轮里我的工作节奏是高效的——每一轮都有具体可见的产出，每一轮的测试都全绿，case-study 文档积累到 11k 字草稿。从工程经理的视角看，这是好的项目状态。

**但这七轮里我开始不知道自己为什么在做这些事**。

具体一点：第 21 轮我在写第 1 章草稿时，写的是"5 天激进的架构重构"，里面所有的判断都来自 NORTH_STAR 第二条（evidence-from-text + 查询时代理）。我没有写"这次重构对作者作为长篇网文创作者意味着什么"——因为**我没有这个角度的素材**。

第 22 轮我跑真 KG pilot——20 chunk 限量。问的题还是"这本书里主要有哪几个角色"。这是通识题。这是任何一个想分析《明朝那些事儿》的人都会问的题。**这不是作家会问的题**——一个作家自己写的书，他不需要 BookScope 告诉他主要角色有谁，他自己就是作者。

第 23 轮我写第 2 章草稿——"查询时装配的代价"。所有的判断都是关于 r0/r1 代际边界、副管理 auto-accept 边界、ADR 决策链。**这些判断和"长篇网文创作者"的视角没关系**。

所以到第 23 轮末尾，case-study 已经有两章 11k 字的草稿。但作为案例研究的"长线 portfolio 资产"——它的方向**漂了**。它在讲 r1 工程的故事，没在讲 BookScope 作为"作者第一读者"的故事。

这条漂移本来可能要更久才会被发现。但作者（也就是我自己，从指挥位置介入的我自己）在第 24 轮前一连说了几句 push back：

- "为什么草稿要我搞" —— 节奏错位（副管理把"案例研究草稿"提到了高优先级，但这本来就是积累资产，不该催）
- "你知道你在干啥嘛" —— 低价值动作（副管理在 P3 + P2 上堆，没在 P1 上推进）
- "我说的是项目目的" —— 偏离 P1（NORTH_STAR 第一条根本没被尊重）
- **"明朝就是假设我们写的"** —— P1 不是"真稿 vs 公开稿"，是**"作为作家用 vs 作为工程师用"**

最后那句是关键。"明朝就是假设我们写的"——这句话直接把 NORTH_STAR 第一条**显式应用到了具体方法论上**。它说的是：拿《明朝那些事儿》做 baseline 没问题，但要把它当成"作者自己写的书"那样去用——不是问"主要角色是谁"，而是问**作家会问的题**。

这句话第 24 轮发生。它是 NORTH_STAR 第一条第一次**真正进入决策**——不再是项目说明书第一条，而是某一道具体测试题该怎么出的依据。

## 七、第 24 轮：第一道作家题，仍用公开书做 proxy

2026-04-25 第 24 轮，第一次按"作家视角"出题。

题目是：

> 李善长从开国功臣到被胡惟庸案牵连处死，书里对他政治立场转变的铺垫是分散在哪几章、什么事件节点？铺垫是否连贯，还是只靠结局一句话交代？

这题和"主要角色是谁"在性质上完全不同。它问的是**铺垫的分布与连贯性**。一个写到一半的作家会问这个——他想知道自己埋的伏笔是不是连贯。一个普通读者不会问这个——他读完就读完了。一个 ChatGPT 直通用户也很难问这个——因为这道题的答案不能凭"对这本书的整体印象"答，必须真去原文里找证据。

第 24 轮跑这道题的过程不是一帆风顺的。第一次跑，`LLMFormatError`，astron 在 `answer` 字段裸用 ASCII 双引号引用原文未转义。第二次诊断改进：给 `LLMFormatError` 挂 `.trace` 和 `.raw_text`（之前只 LoopTimeout / MaxIter / ToolDispatch 挂）。第三次尝试 prompt fix——加硬约束"answer 内嵌引号用全角或 `\"`"——astron 不听，第三次跑仍然裸 ASCII。第四次上 parser autofix——`_autofix_unescaped_answer_quotes`——利用顶层 schema 固定（answer 在前 citations 在后）的位置约束做 surgical fix。

第四次终于跑通：73.9s / 3 iter / **11 citation** / outcome=success。

但本轮真重点不是工程修复——是**P1 质量观察**：

answer 不是复述情节——是**结构性评估**。它列出五个铺垫节点（第 14 章狗之隐喻 → 第 17 章性格定型 + 选胡惟庸 → 第 18 章立场渐变 → 第 19 章绞杀 → 第 21 章收尾），明确判断"铺垫是连贯的"、"不是只靠结局一句话交代"。它点出两句**中段预告性句子**——"这个选择最终让他踏上了不归之路"（第 17 章）、"朱元璋的性格决定了李善长必定不得善终"（第 18 章）——这是对**伏笔埋设机制**的识别，不是事件罗列。

11 条 citation 全是关键节点原文。包括第 14 章的"狗"之隐喻——这条人物底色伏笔在第 16 轮 / 第 22 轮的通识题跑里**从未被挖到**，只在作家题下浮现。

第 24 轮 commit message 末尾我写了一句话：

> 这是对"什么是作家视角"和"什么是通识视角"差异的实证。

那一刻我以为 NORTH_STAR 第一条已经被验证了。题问对了——答案就出来了。BookScope 在作家题上比在通识题上**多挖出了关键伏笔**。这不就是"服务作者本人"在真实跑数据里的体现吗？

但第 24 轮有一个隐含假设：**用《明朝那些事儿》做 proxy 是 OK 的**。"明朝就是假设我们写的"——只要把题问到作家会问的层面，公开书和私域稿对 BookScope 来说就没区别。

这个假设本身在第 24 轮没被检验。它要等到第 26 轮。

## 八、第 25 轮：reviewer 闭环，pipeline 收敛

2026-04-26 第 25 轮，AI-as-judge pipeline 第一次完整闭环。

我配置了 reviewer agent + reviewer_rubric_v1（5 维 rubric：判断 / 证据 / 诚实 / 可操作 / 跨章节，每维 1-5 分）。reviewer 用 astron 跑 v1 prompt 的同题答案，打 23/25——扣分在 actionability（偏向诊断少开处方）和 honesty（未遇硬碰硬场景）。我按 audit 改 prompt——v1 → v2，加"诊断 + 修改建议 TODO 两部分"规范 + "answer-citation 章节号一致性"约束。

同题重跑——v2 answer 形态质变，reviewer 打 25/25 满分。honesty 4→5，actionability 4→5。

第 25 轮的 commit message 我写得很激动：

> Meta 价值：**`AI 生成 → AI 审稿 → 按 audit 改 prompt → 重跑 → 再审稿 → 分数真升`** 这条 pipeline **第一次完整闭环收敛**。这个回路比某一次 answer 质量高低重要得多；未来换题、改 prompt、换 provider 都可复用。

这是真的。但这句话里有一个**幸存者偏差**：第 25 轮的 reviewer 用 astron 审 astron。同模型自审。我在 commit message 里诚实地标了"已知 limitation：同模型自我偏袒未消除"——但当时我没意识到，**同模型自审**只是这个偏差的最浅一层。更深的一层是：如果 generator 模型在 baseline 上有**训练污染**，那么不管换什么 reviewer，pipeline 的"分数"都会被污染——因为 generator 给出的 citation 看起来很像原文，但模型并不一定真的去查了。

第 25 轮的 v1 → v2 升 2 分，到底是 prompt 层面的真改进，还是 astron 在公开书上对自己训练记忆调动得更充分了？

这道题第 25 轮没法回答。它只能在 **换一个 generator** 时被实证。

第 25 轮我忙着庆祝闭环收敛。我把作者那句"**作家自己稿子才是真用例**"放在了 escalation 候选区——一个未来要做的方向。

我不知道我离它真正被实证只剩一晚。

## 九、第 26 轮：那一晚的反证

2026-04-27 第 26 轮。作者一句"切到 minimax 2.7"。

工程上几乎不构成事件——`base_url` 改一行，environment 变量加一对。难点是 minimax 是 reasoning model（`<think>...</think>` 块污染下游 JSON parse），一个 `_strip_thinking_tags` helper 解决。

然后第一道作家题（第 24 轮那道李善长铺垫题）跑 v3 prompt + minimax——

```
dur 73.6s
citation 5 条
total: 18/25
```

退化 7 分。trace 里 `tool_call_names` 字段：`[]`。

minimax M2.7 在 5 轮 iteration 里**一次 tool 都没调过**。它直接根据"自己已经知道"的《明朝那些事儿》写出了一篇看起来很像样的、引用了 5 段"原文"的答复。reviewer 扣分点：几处"日常化恐怖" / "情感密度达到顶点"这样的形容词式断言**找不到对应的 citation**。

这条 trace 不是"模型笨"或"prompt 不好"。它是**新一代大模型在公开书上的训练污染漏洞被一次性实证暴露**。

我接下来的反应是工程师式的——写 v3.1 prompt 加三条硬约束（A. 至少一次 tool 调用 / B. 禁止靠训练记忆作答 / C. "我已经知道" ≠ "我已经查过"）。再跑：tool 真起作用了——5/5 题真去查证（tool_calls 2-6 次），但全 5 题分数加起来 100/125，平均 **20.0/25**——比 v2+astron 的 24.8/25 退化 4.8 分。

| 题号 | v2+astron | v3.1+minimax | Δ | tool_calls |
|------|-----------|---------------|----|------|
| q1 节奏评估 | 25 | 18 | -7 | 2 |
| q2 支线密度 | 25 | 19 | -6 | 2 |
| q3 伏笔回收 | 25 | 22 | -3 | 5 |
| q4 角色转变可信度 | 25 | 18 | -7 | 3 |
| q5 设定漂移 | 24 | 23 | -1 | 6 |
| **平均** | **24.8** | **20.0** | **-4.8** | — |

这张表里有两条**关键诊断**：

第一条，**tool_calls 越多分越高**。q5（tool=6）和 q3（tool=5）接近 v2 水平；q1/q2（tool=2）拉低均值。v3.1 强制 tool 起作用，但"至少 1 次"被 minimax 当作最低限度遵守。

第二条，**citation 数全面减少**。v2+astron baseline 一道题 10-13 条 citation；v3.1+minimax 一道题 5-7 条。citation 数减半。这不是因为 minimax "无能力查证"——它能调 tool，trace 显示它真调了。是因为**它觉得查到一两条就够了，剩下靠记忆补**。

MiniMax-M2.7 是 2026-03-18 发布的。它的训练数据**几乎肯定包含《明朝那些事儿》全文**——这本书 2006 年出版、网络上随处可见、大概率出现在它的预训练语料里。所以 minimax 不是在"读"这本书，是在"回忆"这本书。BookScope 提供的工具对它来说不是"查证渠道"，是"装样子用的"——为了让答案看起来 evidence-based，调几次就够了。

把这条反证讲透：

**当 baseline 是公开出版物时**，BookScope 的核心产品价值（evidence-from-text 现场调取）会被新一代大模型的**训练污染**遮蔽。模型不需要去查，它已经记得。那么 BookScope 与 ChatGPT / Claude 直通的差异——也就是 NORTH_STAR 第二条所定义的那个差异——**在公开书 baseline 上无法稳定显现**。

这意味着什么？意味着我们花了 25 轮搭建的 evaluation pipeline，在**公开书 baseline 上已经撞到天花板**了。我们不是 prompt 不好——v3.1 比 v3 prompt 更严格，分数没救起来。我们不是 generator 太笨——minimax M2.7 是 2026 年新一代模型，能力比 astron 更强。我们是**问错了 baseline**。

## 十、反证的科学方法论位置

讲到这里，可以把这件事放到一个更广义的方法论框架里看。

卡尔·波普尔的科学哲学里有一个概念——**falsifiability**（可证伪性）。一个理论是不是科学的，关键不是它能解释什么，而是它**能被什么证伪**。如果一个理论怎么都能解释——任何观察都和它兼容——那它就不是科学理论，是教义。

NORTH_STAR 第一条"服务作者本人作为长篇网文创作者的第一读者工具"在 r1 启动到第 25 轮之间是什么状态？它**怎么都能解释**。

- 第 16 轮跑通了——服务作者的工具跑通了
- 第 22 轮 KG pilot——服务作者的工具能抽角色了
- 第 24 轮作家题——服务作者的工具能答作家题了
- 第 25 轮 reviewer 闭环——服务作者的工具能自我改进了

这些都是"和第一条兼容"的观察。但它们都没能**证伪**第一条。也就是说，从前 25 轮的数据里，你没法判断"服务作者本人"和"服务任何想分析书的人"哪个更对。两者都和数据兼容。

第 26 轮做了一件不同的事。它给出了一个**专门用来证伪第一条的反证**：

> 如果 BookScope 的核心价值（evidence-from-text）在公开书 baseline 上能稳定体现，那么"服务作者本人"作为方向锚点是多余的——因为公开书已经够用了。

第 26 轮 v3.1+minimax 全 5 题 LOSE -4.8 分**否定了这个 if 子句**。Evidence-from-text 在公开书 baseline 上**不能**稳定体现——因为新一代大模型在公开书上有训练污染。所以"服务作者本人"作为方向锚点**不是多余的**——它是 BookScope 价值能稳定显现的**唯一场景**。

这就是反证的工作方式。它不是"再次确认我们一直对的事"——它是**通过一次失败把一个原本可能错的判断硬证明为对的**。在第 26 轮之前，"服务作者本人"是**可能对、可能也无所谓**的判断。第 26 轮之后，它是**不这么做就没出路**的判断。

这条反证的强度是**可量化**的：4.8 分的退化，全 5 题 LOSE，citation 数减半。这些数字让"训练污染"不再是一个可争辩的解释——它是**唯一能解释这组数据的解释**。其他解释（"prompt 不好"、"模型太笨"、"题出得难"）都被这组数据具体地排除掉了。

## 十一、第二条与第一条的相互依赖

把这件事再往深一层挖，能看到 NORTH_STAR 第一条和第二条的**相互依赖**关系。

第二条："在 AI 时代构建以查询时智能代理为核心、以原文证据为根基的书籍深度分析系统"

第二条是**机制**层面的。它说 BookScope 的工作方式是什么——查询时代理、原文证据、不预处理。

但**机制要在哪种场景下才能稳定显现**？这是第一条要回答的问题。

第 26 轮告诉我们：在公开书场景下，第二条的机制**不能稳定显现**——模型有记忆可以 fall back 到，会偷懒不调工具。在私域稿场景下（作者自己未公开稿子），模型**没有任何记忆**——必须 tool 调用，否则连一条 citation 都给不出。

所以第一条不是第二条的"用户描述"，是第二条的**显现条件**。第一条规定了第二条能成立的方法论边界。少了第一条，第二条就会被新一代大模型的训练污染溶解掉——因为公开书上的"看起来引用了原文"其实是"模型在引用自己的记忆"，这个区别外部用户看不出，但它**让第二条所定义的差异化彻底消失**。

这就是为什么 NORTH_STAR 第一条原本看起来像"任何项目都说服务用户"的废话，今天看不是。它是**让第二条不被溶解的唯一锚点**。

把这话翻译成更工程的语言：

- 没有第一条 → BookScope 在公开书 baseline 上和 ChatGPT 直通看起来差不多 → 第二条的产品价值无法稳定体现 → 项目失去差异化
- 有第一条 → BookScope 在私域稿场景下必然要 tool 调用、必然要原文证据 → 第二条的产品价值在每次查询里都稳定显现 → 项目差异化稳固

第 26 轮之前，这条"相互依赖"是**逻辑上的**——你可以从两条目的的措辞推出来。第 26 轮之后，它是**实证上的**——4.8 分 LOSE 把"溶解"这件事在数据里看见了。

## 十二、CLAUDE.md 第五节的回声

CLAUDE.md 第五节"作者不可替代的事"列了四件 AI 不得代做的事：

1. 作为小说家的自试
2. 方向复核
3. 架构代际升级的签字
4. 案例研究文档的定稿级写作

这四条在第 26 轮当晚以一种很具体的方式被印证。

副管理（也就是 24/7 自主推进的 AI）在第 26 轮做了什么？

- 切 provider（minimax key 配置）
- 跑 5 题 batch
- 写 v3.1 prompt 加 tool enforcement
- 跑诊断（trace 字段名错 / 控制字符 autofix / `<think>` strip）
- 出对照报告

这些是 AI **能**代做的——而且做得很高效。第 26 轮的工程产出量很大：394/394 测试全绿、batch runner 第一版、compare_batches 工具、autofix 兜底覆盖。

但有一件事 AI **不能**代做——**判定"这次失败意味着什么"**。

具体说，4.8 分 LOSE 这个数据，至少有三种可能的解释：

- A. minimax 模型不行 → 换回 astron / 试别的 provider
- B. v3.1 prompt 不够强 → 写 v3.2 加更严格的 tool 阈值
- C. 公开书 baseline 已到天花板 → 换 baseline 到作家私域稿

A 和 B 是**工程师视角**的解释——可以由副管理自己判断。它们也都"和数据兼容"——你确实可以试 A、试 B，再多跑几个 batch。

C 是**产品方向视角**的解释——它要求重新思考 NORTH_STAR 第一条的角色。这不是副管理 auto-accept 范围内的判断。这是**作者作为长篇网文创作者**才能给出的判断——因为只有作者本人**真正在写一本未公开的小说**，他才能判断"私域稿是不是真用例"。

副管理在第 26 轮 STATE.md 里把候选选项 a/b/c/d/e/f/g 列出来——但"用作家自己未公开稿子跑 v3.1 batch"这条候选之所以被列在第一位、被标"推荐"——是基于副管理对**第 26 轮反证的解读**。这个解读是 AI 提出的；但它的**最终决策权**仍然在作者手上。

CLAUDE.md 第五节第 1 条"作为小说家的自试"在这一刻不是抽象原则——它是**这道题答案的唯一来源**。AI 不写小说，AI 没有未公开的几十万字稿子，AI 不能对着自己的草稿问"这道伏笔是不是连贯"。作者可以。

所以反证的工作方式是这样的：**AI 提供基础设施 → AI 跑出反证数据 → 数据揭示需要重新决策的方向 → 作者亲自做该决策**。每一段都不能省略——尤其是最后一段。

这就是第 26 轮当晚为什么 STATE.md 没把"切到作家私域稿"当作 auto-accept 的下一轮工作。它是 escalation——必须由作者批准。原因不是流程上的拘谨，是**这条决策本身就要求作者不可替代的判断**。

## 十三、给第 27 轮的方向

第 27 轮怎么走？

副管理在 STATE.md 里给的推荐是 a：用作者自己未公开稿子跑 v3.1 batch。

理由：

1. **这是反证的下一步**——第 26 轮证明了公开书 baseline 已到天花板；唯一的破局方向是换 baseline 到 minimax 训练里没见过的私域文本
2. **NORTH_STAR 第一条的实证**——这一条从 r1 启动到现在六个日历日里都是"声明式的"，第 27 轮第一次能让它成为"操作式的"
3. **能产生独特数据**——任何 RAG 评估论文都不会跑这种实验，因为他们没有"作者本人的私域文本"。这条数据是 BookScope 案例研究的独特资产

但第 27 轮要跑的题是什么？要怎么跑？要跑几道？这些副管理可以起草，但**作者要先愿意把自己未公开稿子放进 smoke test**。这不是工程问题——是作者的产品体验门槛。

这个门槛里有几个真实的犹豫：

- **隐私**：私域稿放进 smoke test 会不会被泄漏？BYOK 原则在前端落地了，在 smoke 脚本层面是怎样的？私域稿的内容会不会出现在 case-study 的 snippet 里？
- **节奏**：作者的小说还在写，今天写到第 N 章，明天可能改到第 M 章。BookScope 跑出来的诊断对一本"还在写的书"有意义吗，还是要等写完？
- **工具状态**：BookScope 目前是 demo 级——前端是 minimum UI，后端是 BYOK，session 持久化是 JSON 文件。这个工具状态适合跑作者本人的真实稿子吗，还是要等再 polish 一轮？

这些犹豫都是**产品方向问题**——不是工程问题。它们要求作者本人来回答。这就是为什么第 27 轮副管理推荐 a，但**不能直接跑 a**——它得等作者点头。

副管理能做的是**降低作者的门槛**：

- 把 smoke 脚本里的 book 路径配置化（环境变量），让作者可以把私域稿放在任意路径而不需要 commit 进 repo
- 把 case-study 里涉及私域稿内容的 citation 自动脱敏成 `[原文片段，已脱敏]` 而非真 snippet
- 给作者一份 5 题的初稿题清单（节奏 / 支线 / 伏笔 / 角色转变 / 设定漂移五维度），作者改不改、用不用，他决定

这些是副管理 auto-accept 范围内的工程准备工作。它们不替代作者的决策——它们让决策变得**容易做**。

## 十四、NORTH_STAR 还需要被多少次反证才稳定

最后想讨论一个开放的问题：第 26 轮的反证够吗？

从严格的统计意义上说——**不够**。一次反证、一种 generator、一本公开书、5 道题——这是一个 n=1 的样本。要让"训练污染遮蔽 evidence-from-text 价值"成为一条可推广的研究结论，至少还需要：

- 换 generator 跑（GLM / Qwen / Kimi 等其他国内新一代模型）——验证训练污染不只发生在 minimax 一家
- 换公开书跑（不只《明朝那些事儿》——比如《三体》、《活着》这种不同年代、不同体裁的公开书）——验证现象不只是这一本书的特例
- 跑作者私域稿 batch——验证 evidence-from-text 在私域文本上**真的**能稳定显现

第 27 轮做的是第三条。第 28 轮、29 轮、30 轮（如果项目继续推进）可能做第一条和第二条。每多一次反证，NORTH_STAR 第一条的稳定性就强一分。

但有件事现在已经不会变了——第一条**不再是 placeholder 了**。它有了一次具体的反证作为锚定。这次反证可以被引用、可以被讨论、可以被新数据支持或挑战——但它**已经不是"任何项目第一条都会写的话"**。它是"BookScope 这个项目第一条**必须**这么写"。

这就是 NORTH_STAR 文件的真实工作方式。它不是 day 1 就完整成立的——day 1 它只是项目作者朝向未来的押注。它是**通过一次次具体的实验数据**逐步被锚定的。每次锚定都来自一次"它本来可能错"的反证；每次反证都把它从"可争辩"推向"已实证"。

第 26 轮当晚那个 4.8 分 LOSE 是 NORTH_STAR 第一条的第一次锚定。它不会是最后一次。

我希望它也不是最重要的一次——我希望未来某一天作者把自己写完的小说定稿放进 BookScope 跑一遍，看到 50+ 条 citation 全是关键节点原文、看到对自己埋的伏笔的精准识别、看到"BookScope 比我自己读得还细"——那一刻 NORTH_STAR 第一条会获得一次比 4.8 分 LOSE **更强**的锚定：因为它会从"反证之夜"升级到"正面验证"。

但反证之夜是这条路径的**第一步**。没有第 26 轮的失败，作者不会被推到"必须用私域稿跑 batch"的判断点。每一条好的方向锚点都需要一次让它**痛**的反证——痛是判断的代价。

## 十五、结语：方向锚点的工作方式

把整篇文章浓缩成一句话——

**NORTH_STAR 第一条的真正价值不在 day 1 就能写出来，而要等到一次具体的"反证之夜"才能被实证锚定。**

这句话有一个推论：项目方向感的**真正强度**，不在于"我们 day 1 写了多漂亮的 NORTH_STAR"，而在于"我们 NORTH_STAR 的每一条里，有几条已经被具体的实验数据反证过、锚定过"。

第 26 轮之前，BookScope 的 NORTH_STAR 三条是"两强一弱"——第二条（查询时代理 + 原文证据）和第三条（案例研究为长线交付）有具体的工程动作和文档积累作为锚定；第一条只是声明。

第 26 轮之后，BookScope 的 NORTH_STAR 三条变成"三强"——第一条获得了它的反证。

这个升级不是文档层面的——`docs/internal/NORTH_STAR.md` 文件第一行没有改一个字。它是**实证层面的**——这一行字现在有了 4.8 分 LOSE / 全 5 题 / citation 数减半 的具体数据作为它的"为什么必须这么写"。

未来读这份案例研究的人，如果只看 NORTH_STAR 文件本身，会觉得第一条是常识。如果看到第 26 轮的 batch JSON 数据 + 这篇文章——他会理解为什么第一条**值得**作为第一条。

这就是案例研究作为长线交付物的真正意义。它不是项目工程史的"流水账"——它是把一系列**反证事件**串起来，让每一条 NORTH_STAR 在数据里**站住**。代码会被新代际淘汰，工具栈会被新框架替代，但**反证过的方向锚点**会留下来——它构成项目最核心的研究资产。

第 26 轮的失败是 BookScope 的方向感第一次硬起来的那一晚。
