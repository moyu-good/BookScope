## 序：同一根脊，换了三次承载

一本书有章。一份红头文件有条款。一场会有议程项。

这三样东西看起来八竿子打不着——一个是小说家的叙事，一个是机关的指令，一个是会议室里几万字的口水话。但 BookScope 这一程做的事，是发现它们其实是同一种东西的三个样子：**一份长文档，切成若干分析单元，每个单元抽出带原文证据的结构化记录**。章、条款、议程项，都只是"分析单元"这个抽象的不同填法。

这件事不是想出来的，是长出来的。chapter-12 收尾时，BookScope 还只会读书——人物关系图、节奏曲线、伏笔追踪，全是围着"叙事"转。那一章末尾沉了一条方法论：整本书的结构化功能有套统一骨架（单独端点 + 按需 fetch + 长上下文出 JSON + 三可靠性守卫）。当时这条只在"书"这一类题材里成立。

这一程把它捅破了一层：作者 2026-06-24 拍板，BookScope 从"读整本书"扩成"读懂难读长文档"，第一个新垂直是红头文件（公文）。公文做透之后，会议又接上来当第二次验证。两次实战跑下来，那套"读书的骨架"被证明根本不是"读书的"，是"读长文档的"——把分析单元从"章"换成"条款"、换成"议程项"，骨架一行不用改，照样跑。

于是有了这一章要讲的两件事：**一台引擎怎么长出三根脊**（架构主线），以及**接一个新垂直该怎么走才不瞎撞**（七步方法论，这一程固化成了一条 skill）。

但这一章不打算只讲成功。七步里有一步明显比别的步生——第四步"派生视图"。公文上它靠大量换皮撑住了场面，会议上它露了底：首炮只兑现了一个最简单的视图，真正难的几个一个没做。这一节会老老实实讲它弱在哪、为什么弱。这是研究笔记，不是产品宣传册。

## 一、从"读书"到"读长文档"：方向是怎么翻过来的

先说清这个转向不是 BookScope 自己想扩张。是作者 2026-06-24 拍的板。

起因很具体：作者要看懂政策公文，又不想找人解读。红头文件这种东西，普通人读起来就两个字——头疼。术语绕、口气端、关键信息埋在"原则上""研究研究"这种话里。作者的判断是，BookScope 那套"翻你这份文档、每条结论标出处"的本事，拿来啃公文应该一样管用。

这个判断背后是一次架构上的认账。回头看 chapter-12 之前，BookScope 嘴上说"服务任何长文本创作者/读者"，手上做的全是叙事分析。人物、情节、伏笔、关系——这些词一个都套不到公文上。公文没有人物弧线，只有谁该干什么；没有伏笔，只有这条凭哪个上位法。如果"读书"的代码真的只会读书，那"通用"就是句空话。

公文被选成第一个新垂直，有个很实在的理由：**前人经验厚**。国家有 GB/T 9704 公文格式标准，等于现成的 ground truth——发文字号长什么样、文种有哪些必备要素，国标里白纸黑字写着，抽出来对不对一查便知。法律信息学这门学科攒了几十年的引用网络、立法演变追踪、条款抽取方法。接一个新垂直前先扒前人经验、别瞎造，这是 memory `project_vertical_analysis_methodology` 立的硬规矩，公文恰好是这条规矩的正面教材。

NORTH_STAR 跟着改了（commit `1090a4f`，2026-06-24）。定位从"读整本书"广义成"读懂难读长文档"，一句话点透引擎和场景的关系：**引擎通用、场景具体**——底层一套"整份读一次出带证据的结构 + 查询时按问派生分析"的引擎，书是第一个做透的场景，公文是第二个垂直。

这一改不是文字游戏。它把"通用"从一句愿景变成了一条要兑现的承诺：如果引擎真通用，那接公文就应该是"换单元"而不是"重写"。这个承诺，接下来由代码来还。

## 二、章脉 → 文脉 → 会脉：一台引擎的三根脊

NORTH_STAR 那句"整份读一次出带证据的结构"，落到代码里有个名字——**脊**。

脊是 chapter-11 那条"测量仪器先于实验"母题往架构层走的产物，原始决策见 memory `project_chapter_spine_turn`（ADR-010）。一句话说清它干嘛的：几百万字的书，整本精读**一次**，逐章产出带原文证据的结构化记录；下游十几个功能不再各自重读全文，全从这一份记录派生。这一份记录就是脊。它是整个分析的单一事实源——脊建对了，下游全是纯计算或一次轻 LLM，秒出；脊建错了（漏单元、序号塌缩、证据锚错），下游全脏。

书的脊叫**章脉**（`chapter_spine.py`）。这一程的事，是它长出了两根同胞：

- **文脉**（`doc_spine.py`，893 行）——公文的脊。一份红头文件精读一次，出"头要素 + 逐条款"的带证据结构。
- **会脉**（`meeting_spine.py`，847 行）——会议的脊。一份会议记录精读一次，出"会议头要素 + 决议 + 行动项"的带证据结构。

三根脊摆一起，骨架是一模一样的三维：

| | 章脉（书） | 文脉（公文） | 会脉（会议） |
|---|---|---|---|
| 文档级身份维 | 书名 / 作者 / 题材 | 发文字号 / 文种 / 发文机关 / 主送 / 成文日期 | 会议主题 / 时间 / 主持人 / 参会人 / 记录形态 |
| 内容主体维 | 逐章：人物 / 事件 / 关系 | 逐条款：事项 / 指令类型 / 责任主体 / 时限 / 依据引用 | 决议 + 行动项：定了什么 / 谁要做 / 时限 / 含金量 |
| 门控开关 | 题材（决定亮哪些功能） | 文种（决定该有哪些必备要素） | 记录形态（逐字稿能追原话，纪要追不到） |

身份维 + 内容维 + 一个门控开关。三根脊全是这个形状。文档级身份维负责"这份文档是什么"，对公文还能拿 GB/T 国标验；内容主体维是大头，是逐单元淘出来的干货；门控开关决定这份文档能做和不能做哪些分析。

更关键的证据藏在代码复用上。会脉 847 行，看着不少，但它**一行没碰** `doc_spine` / `chapter_spine` / `redhead_codebook` 现有模块——只 import helper（commit `7a4c1a3` 的"变化"节白纸黑字记了这条铁律）。底层那台分段并发抽取的机器（`exhaustive.run_segments`）、那套 JSON 三层解析兜底（`utils/json_parsing`）、那个把文档摆前面让同一份文档不同功能共用前缀缓存的 system 拼装（`build_longctx_system`）、那条靠 `finish_reason=length` 信号续抽的截断抢救——会脉全是直接拎来用，单元从"条款"换成"议程项 + 结论项"，仅此而已。

这就是"一台引擎三根脊"的硬证据：不是三套各写各的代码长得像，是**同一套底座，喂进不同单元，吐出不同脊**。

## 三、公文教的三件事：第一次实战

公文是七步方法论的第一次真刀真枪。它教了三件事，每件都进了后来的 skill。

**第一件：跨文件才是杀手价值，单份是地基。**

单份公文能做的事——大白话翻译、办事清单、硬信息时间轴——说穿了是把书的功能换个皮。书有"逐章摘要"，公文就有"大白话翻译"；书有人物关系图，公文就有依据链网。换皮做得再溜也是地基，不是这个垂直立得住的理由。

公文真正值钱的地方在**跨文件**。一份通知引了三个上位法、落实两个文件、废止一个旧规定——这张引用网络，人工对读对不过来。BookScope 把一摞公文摆一起，连成"依据链网"（commit `182eb11`，作者注里直接标了"跨文件命门"）：每个文件靠发文字号当身份，引用按效力层级往上指。这是跨文件视图，单份文件根本没有。`cross_doc.py`（639 行）+ `cross_doc_views.py` 撑起的就是这一层。

这件事抽象成 skill 第三步"选角度"的一条铁律：**换皮别当成就，发明区才是价值**。功能不从"引擎能搬什么"长出来，从"这类文档的读者想搞清什么、而现在搞不清"长出来。公文读者最搞不清的就是"这文件凭哪些依据、跟别的文件什么关系"——依据链网是这个痛点的解药，不是引擎能力的炫技。

**第二件：含金量得判真金白银还是空头，判据是钱学森的开环闭环。**

公文条款不是生而平等的。"各单位务必于 6 月 30 日前完成整改，逾期通报"和"鼓励各地积极探索创新做法"是两种东西——前者有责任主体、有时限、有罚则，后者是号召。读者要的不只是"这条说了啥"，是"这条是真要办还是说说而已"。

这一刀切下去的判据，作者用的是钱学森控制论的开环/闭环（`redhead_codebook.py` 的 `SUBSTANCE_LEVELS`）。**闭环**——有责任主体 + 有时限 + 有考核罚则，反馈回路是闭合的，这是真金白银。**开环**——纯号召，没主体没期限没下文，回路开着，大概率漂没，这是空头倡导。这把尺直接拿来给每条条款评含金量，1.6.1 的"利害与风向"（commit `2b05df9`）更进一步，按读者角色读出每条对你是机会还是风险，附条文是真金白银还是十年二十年的空头支票。

判含金量这件事，进了 skill 第三步的另一条："每个功能再深一层，加判断层，别停在提取罗列。"浅是把条款列出来，深是在同样的证据上加一个判断——这条是闭环还是开环。深读三层镜头（`WP-redhead-deep-reading-lenses`）就是这条的展开。

**第三件：会咬人的判断要双向守卫，宁缺毋滥。**

公文跨文件还有个更险的功能：扫上下级一致性——下级文件有没有跟上位法"走样"。这个判断会咬人。说一份地方规定"抵触上位法"，读者可能真拿去申诉、去较真。判错一条，代价是误导一个真去办事的人。

所以这条走双向守卫（接立法法的"抵触 vs 合法变通"，commit `53360fe`，作者注里标了"降 cry wolf"）：两端原话任一锚不到就丢，宁可漏报不可虚报。这是把"狼来了"防护焊进了会咬人的判断。

这三件事——跨文件杀手、开环闭环判含金量、咬人判断双向守卫——后来都成了 skill 里反复出现的桩子。公文这一遍，等于把七步走了一趟、把坑踩了一遍。

## 四、第四步"派生视图"是最生的一环（诚实写最弱环）

讲到这里该停下来说句实话。七步方法论不是七步一样硬。**第四步"派生视图"明显比别的步生**，是这套方法论现在最不成熟的一环。这一节专门讲它弱在哪、为什么弱——藏着不写就是把研究笔记写成宣传册。

先说第四步是干嘛的。第三步"选角度"选定了这个垂直要做哪些功能（公文选了依据链网、办事清单、利害与风向……），第四步是把每个角度落地成一个视图，从脊派生出来。skill 把派生分了三档，越靠前越省：纯计算从脊派生（0 次额外 LLM，秒出）、逐条带身份判（同 relevance，一次并发 LLM）、一次全局跨单元推理（最贵）。

听起来很顺。问题在于：**这三档里，只有第一档（纯计算派生）是真的稳、真的可复制；越往后越是每个垂直得重新啃一遍的硬骨头，根本谈不上"照套路派生"。** 第四步现在的成熟度，全靠第一档那些便宜视图撑着场面。

证据在会议首炮里看得最清楚。

会议设计稿（`WP-1.7-meeting-vertical.md`）洋洋洒洒列了一堆派生视图：纪要速读、行动项台账、我的行动项、悬而未决、立场与弦外、谁担了什么、跨会承诺—兑现、跨会议题滚动——七八个视图，七八个维度，设计上分工得清清楚楚。

实际首炮落地了几个？**一个**（commit `7a4c1a3`）。

落地的那一个是行动项台账——恰好是最便宜的纯计算派生：从会脉的 `action_items` 直接拎出来排个序，0 次额外 LLM。连带着 `loose_end`（owner 空或 due 空 = 悬而未办）也是 BE 纯计算判的，不让模型打分。这一档兑现得很干净：meeting-01 真跑下来，4 条行动项里 Eng-B 的鉴权任务有人有期判成闭环真金白银、Eng-D 回的那个 issue 因为没说截止时间被标成 loose_end 空头表态、而且没编一个 owner 糊上去，evidence 4 条全核过。第一档名副其实。

但设计稿里真正值钱的几个，一个没做：

- **`open_issues`（议而未决）首炮恒空 `[]`**——schema 先占了个位，第二炮再填（`meeting_spine.py` docstring 写得明明白白）。会议最大的黑洞"讨论了但没拍板"，首炮就是个空列表。
- **跨会承诺—兑现追踪**——设计稿里点名的会议杀手价值（"张三第一次会承诺的事第三次会兑现没"），属于第三档"一次全局跨单元推理"。**零代码。** 现在只有会脉这一份单会的脊，跨会那一层（类比公文的 `cross_doc`）还没建。
- **立场与弦外**——招牌深度，读多方真实姿态（谁真同意谁软反对），属于评估层最难的活。**没碰。** 设计稿自己都把它排到最靠后，理由是"最吃输入质量、最容易破证据红线"。

换句话说，会议这个垂直在第四步上只兑现了 1/N——一个最简单的纯计算视图，差异化最高的那几个全在 to-do 里。

那为什么公文看着不显得这么虚？因为**公文用换皮把第二档、第三档的量铺出来了**。`redhead_*.py` 加 `cross_doc*.py` 一共十个文件，看着派生视图很丰富。但拆开看，相当一部分是把书的现成功能换个皮——大白话翻译是逐章摘要换皮、办事清单是"谁做啥何时依据"的清单换皮。换皮派生有个隐蔽的好处：**底座现成、风险低、出活快**。真正难的是那些没法换皮的——依据链网这种跨单元全局推理（第三档），公文也是单独啃了一阵才立住（`182eb11` 的"复活"二字透了消息：它中间塌过、修过）。

所以第四步的真实成熟度是这样的：

- **第一档（纯计算派生）**：成熟。从脊取字段、排序、聚合，机制稳定，换个垂直照搬。会议的行动项台账、公文的指令清单都是这一档，可靠。
- **第二档（逐条带身份判）**：半成熟。靠 `redhead_relevance` 那套"逐条判 + 并发 + 核验"撑着，换垂直要换 bearing 标签（公文是义务/利好/条件，会议是承诺/指派/知会），但骨架能复用。算半条腿站稳。
- **第三档（跨单元全局推理）**：**最生**。`cross_doc` 那套"脊 + 一次全局推理 + 锚回真实单元"在公文上跑通了，但每接一个垂直，跨单元连的关系类型是全新的——公文连"文件引文件"（依据/落实/废止），会议连"人对人承诺—兑现"，这俩根本不是换皮，是两种完全不同的关系。skill 里那句"跨单元连的关系按垂直不同，别想当然换皮"就是这个意思。第三档现在更像"每个垂直各写一遍、彼此长得有点像"，离"照套路派生"差得远。

把话说死：**第四步现在能稳定复制的只有第一档。第二档靠一个现成模块勉强撑住。第三档——也就是每个垂直真正的杀手价值所在——基本是每来一个垂直就得重新设计一次的发明活，谈不上方法论。** 会议首炮只做了第一档、把第三档全推到后面，不是偷懒，是第三档本来就没有可照搬的套路。

这一环弱，根子在哪？根子在**"派生"这个词把难度抹平了**。纯计算确实是派生——从脊取数排个序。但跨单元全局推理叫"派生"就有点名不副实了：它要重新设计关系类型封闭集、重新写全局推理的 prompt、重新处理"锚不回真实单元就丢"的边界、还得配本地兜底防 LLM 碰运气（`_local_basis_relations`）。这哪是从脊"派生"，这是在脊上面又盖了一层新工程。把这层叫"派生视图"，等于用一个轻飘飘的词盖住了最重的活。

诚实的结论：七步方法论里，**定单元、建脊、证据为根这三步是真硬**（公文会议两遍都验得很扎实），**派生视图这步是个筐**——第一档名副其实，第二档凑合，第三档是把"还没有方法论的部分"也塞进了这一步。下一个垂直（合同、判决书）接进来时，第一档大概率还是照搬就行，但第三档八成又得从头啃。skill 里这一步写得最像"套路"，恰恰因为它的难处被"派生"这个词遮住了。这是这套方法论将来最该补的地方。

## 五、会议验的两件事 + 压后的一件事：第二次实战

公文把七步走了第一遍，会议是第二遍验证。第二遍的价值在于：哪些是公文的偶然、哪些是跨垂直的通则，得有第二个样本才分得清。会议验出了两件通则，也照见了一件得压后做的事。

**验证一：主单元怎么定，公文和会议分道扬镳——这一步是真硬。**

公文的条款是"内容即产出"：每一条条款本身就是要读的东西，逐条抽就对。会议不是。会议的发言轮是过程——一场两小时的会几百轮口水话，寒暄、跑题、重复占大头；决议和行动项才是结果，三五条干货。

如果照公文那样"逐发言轮抽"，会抽出几百条"某某说了某某"的流水账，等于把噪声原样搬进脊，正好违背会议读者最核心的痛点——从泥里淘金子。所以会脉的主单元是**结论项**（决议 + 行动项），发言轮降为证据来源：每条决议锚回"是谁在第几轮说的哪句原话"，发言轮当 evidence 用，不当主单元列（`meeting_spine.py` docstring 把这个决定讲得很透）。

这一步分道扬镳，验出了 skill 第一步"定单元"的核心问法：**这类文档是"内容即产出"（逐单元抽），还是"产出埋在过程里"（要先淘）？** 公文是前者，会议是后者。这个区分公文一个样本看不出来——公文恰好是"内容即产出"，单看公文会误以为"逐单元抽"是通则。会议这第二个样本，才把"定单元要先判内容和产出是不是一回事"这条通则照出来。这是第二次实战不可替代的价值：它把第一次实战里看不出来的"偶然 vs 通则"分开了。

**验证二：含金量开环闭环的判据，跨垂直真的通用。**

公文用开环/闭环判条款含金量。会议的行动项天生适合这把尺：有 owner + 有 due + 有验收 = 闭环 = 真金白银；"回头弄一下"无人无期无下文 = 开环 = 空头表态。

关键证据是复用的颗粒度：会脉判含金量直接 import `redhead_codebook` 的 `coerce_substance`，**框架一行不改**，只把叶子档名换了——公文叫"空头倡导"，会议叫"空头表态"（commit `7a4c1a3` 明确记了这一处差异）。一个判据框架，换两个字的措辞就跨了垂直，这说明开环/闭环不是公文的特例，是判"这条是真要办还是说说而已"的通用尺。会议这个样本把它从"公文的判据"升成了"任何含指令文档的判据"。

**压后的一件：立场与弦外最吃输入质量，所以挪到最后做。**

会议设计稿把"立场与弦外"（读多方真实姿态）定为招牌深度，却同时把它排到功能优先级最靠后。理由是它最吃输入质量——要读出"谁真同意谁软反对"，得有逐字稿的原话语气；纪要稿编辑过、噪声磨平了，根本读不出弦外之音。

所以会脉头要素里有个门控字段 `form`（逐字稿 | 纪要）。立场与弦外只在逐字稿上跑，纪要稿优雅退场（返空 + 一句"这是整理稿，读不出现场语气，建议上传逐字稿"）。这是题材自适应退场（七步第六步）在会议垂直**内部**的一次细分——不光是"公文 vs 书"这种跨垂直的题材门控，同一个垂直内部、同一种文档的不同形态，也要分形态退场。

这件事压后，照见的是 evidence-first 的一条延伸：**输入质量不够的功能，宁可不做，不硬产**。会议比公文更容易破证据红线——结论是埋着的、立场要推断，模型很容易脑补"他其实是反对的"。把最吃输入质量的功能挪到最后、先验证逐字稿质量够不够，是对"没有原文证据就不输出"这条底线的尊重，不是工程上的偷懒。

## 六、七步方法论：这一程固化成了一条 skill

公文走了第一遍、会议验了第二遍，七步方法论被磨得足够清楚，这一程把它固化成了一条 skill（`.claude/skills/vertical-design/SKILL.md`）。

固化的时机不是随便挑的。memory `project_vertical_analysis_methodology` 早就立了规矩：方法论要用清楚之后才固化成 skill，别拿没验过的套路当套路。这跟全局那条"任何开发先设计"的 `design-first` 闸是一条线——`design-first` 管"任何非自明开发先过设计闸"，这条 vertical-design 管"新垂直具体照哪七步设计"，是 `design-first` 在"新垂直"这一类任务上的专用模板。

七步一句话各是：

1. **定单元**——横向怎么分段 + 纵向抽什么（先判：内容即产出，还是产出埋在过程里）
2. **建证据脊**——一份精读一次出带证据的三维结构（身份维 + 内容维 + 门控）
3. **选角度**——三问（内在结构 / 读者痛点 / 换皮 vs 发明区），功能从痛点长出来不从引擎能力长出来
4. **派生视图**——每个角度一个视图，能纯计算就别调 LLM（**这一步最生，见第四节**）
5. **证据为根**——锚原文 / 抽不到留空 / 推断标研判，贯穿全程不是某一步
6. **题材退场**——不对口的优雅退场 + 给一句人话，不产 garbage
7. **视图协同**——一份脊多视图共享缓存 + 别名归一 + 维度不撞脸

这套 skill 最值钱的不是七个步骤名，是后面那张"已验证底座清单"——把"加新垂直直接 import、一行不改现有模块"的十几个 helper 列了出来：脊分段并发抽（`run_segments`）、头要素抽 + 核验（`_build_head_elements`）、跨段全局重排序号（`_renumber`，不被 evidence 覆盖）、含金量开环闭环判（`redhead_codebook`）、跨单元锚回真实单元（`cross_doc`）、别名归一（`build_spine_name_map`）、题材门控（`detect_genre`）……

清单末尾点了一句关键的："**新建只在三处**"——这个垂直的 schema、这个垂直版 codebook（措辞刻度，但开环闭环框架复用）、这个垂直独有的跨单元关系。公文会议两遍都是这个结构：90% 是底座复用，10% 是这个垂直独有的新建。这 90/10 的比例，就是"一台引擎接多个垂直"在工程量上的真实样子。

但这条清单也得配着第四节的诚实读：清单里前面那些（脊、核验、含金量判据）是真稳的底座，照搬就行；末尾那个"跨单元关系"挂在第三档派生上，是每个垂直都得重啃的，"复用 `cross_doc` 范式"复用的只是骨架，关系类型每次都得重新设计。skill 把它和前面那些稳底座并排列，其实拉平了难度差——这是 skill 自己也没说透的地方，记在这里当将来修订 skill 的提醒。

## 七、收尾：通用是验出来的，不是宣称出来的

把这一程放进整套案例研究的脉络里：

- chapter-12 把验过的能力搬上货架，但那些能力全是"读书"的；
- **本章：把"读书"的引擎，验成了"读长文档"的引擎。**

chapter-12 末尾那条"整本书结构化功能统一模式"，当时只在书这一类题材里成立。这一程公文做透、会议接上，把它从"一类题材内的统一"扩成"跨题材的统一"——同一根脊换三次承载单位（章/条款/议程项），同一套底座 import 三遍不改一行。"通用引擎"这四个字，到这一程才算有了代码证据，不再只是 NORTH_STAR 里的一句话。

但这一程更该记的，是它没藏起来的那块短板。七步方法论里，定单元、建脊、证据为根是真硬，公文会议两遍都验得扎实；派生视图那一步是个筐——第一档纯计算名副其实，第三档跨单元推理是把"还没有方法论的部分"也塞了进去，每接一个垂直都得重啃。会议首炮只做了第一档、把杀手价值（跨会承诺—兑现）全推到后面，照出的正是这块短板。

一个把短板写成长板的案例研究是软文，一个老实标出"这一步其实是个筐"的案例研究才是研究。BookScope 这一程真正学会的，不是"通用引擎多厉害"，是"通用到什么程度有代码兜底、到什么程度还是每次重啃"——前者是第一到第三、第五步，后者是第四步的第三档。把这条边界画清楚，比喊"我们做了通用引擎"有用得多。

下一程的候选摆在路上：会议第二炮（把 `open_issues` 填实、把跨会承诺—兑现这个杀手建出来，正好拿来验第四步第三档到底能不能复用 `cross_doc` 范式）、会议题材词进 `GENRES`（现在 `{小说/历史/理论/论文/公文/诗歌/工具书/其他}` 里还没有"会议"，门控这一层待接）、立场与弦外（先验逐字稿质量够不够）、以及第四个垂直接进来时——再看一遍：定单元、建脊、证据为根是不是还那么硬，派生视图的第三档是不是还得从头啃。验第三遍，才知道这套方法论到底站不站得住。
