## 序：秒表说五分钟，但秒表不会说为什么

作者掐了个表：打开安史那本书，等章脉建完，五分钟。

一句"读安史五分钟"扔过来，最省事的接法是把它当成"算法慢"——章脉是整本书精读一次的活，几十段 LLM 调用，慢点正常，那就多开几路并发压墙钟。这个反应几乎是本能的，副管理这次也差点顺着它走。

但秒表只会告诉你花了五分钟，不会告诉你这五分钟花在哪。掐表和诊断，是两件事。真把这五分钟拆开，发现大半根本不在"算法慢"上——安史三十来章、三十九万字，段数本来就少，几路并发早把段全铺开了，再加并发对它一点用没有。五分钟里真正的冤枉钱是两笔看不见的账：一笔是前一天升了章脉的结构版本，全书旧缓存作废，这次是从零冷建整条脊；另一笔更糟——预热的后台线程和用户点开可视化，各自把同一条章脉从头建了一遍，双份 token、双倍墙钟。

这一章讲的就是从这块秒表开始的一程。目标听着简单：依托缓存 + 顶级论文的思路，让章脉建得又快又省，不论什么书尽量进两分钟。做下来是一件干净利落的赢，加上三个把"快一倍"稳稳顶回来的 probe。三个 probe 都花了不少 token，结论却大多是"不行"或"没到底"——但恰恰是这三个"不行"，把"章脉能免费提到多快"这条边界给量出来了。**一个把 NO-GO 老实写下来的性能优化，比一个偷偷 ship 了打折版两倍速的性能优化，值钱得多。**

## 一、起点：作者要的不是"快"，是"又快又省又不更差"

先把目标说准，不然后面三个 probe 全会看走眼。

作者 2026-07-09 把性能目标细化了一版，核心不是单纯的"快"。研究笔记 012 开头记着作者的原话纠偏：**"不是并发——是怎么 token 消耗足够少的同时、解决得更好。"** 三个词绑在一起：token 更少、速度更快、质量不更差。少了任何一个，另外两个都不算数。

这个 framing 直接决定了后面每个 probe 的判据。一个改动如果只让墙钟快、却把 token 或质量赔进去，它算不上真的更快，是拿别的东西换速度——换不换，得作者拍，不是工程能自决的。这条一竖起来，后面三堵墙才立得住：它们拦下的都是"看着更快、其实赔了别的"的路。

目标还分了三档，诚实标了各自的天花板：

- **交互等待 ≤2min**：用户点开一本书到看见结果。这一档能做到，靠预热 + 缓存 + 别重复建。
- **中小书冷建 ≤2min**：几十万字的书从零建脊。现实可及，靠省一半读书量 + 并发。
- **超大书冷建进不了 2min**：几百万字的书，物理上做不到。evidence-first 决定了书至少要完整读一遍才能带原文证据，读一遍就是 token 和时间的地板。这一档只能预热 + 提前提示用户，不能定成硬指标。

第三档这个诚实的地板很重要。它意味着"任何书都进 2min"这句话，从一开始就不该被当成一个能达成的 KPI，而是一个分场景的承诺。把它当 KPI，就会逼自己去做那种"牺牲质量换速度"的事——正是这一程要挡住的。

## 二、先看清地形：长文两条路、一根脊、脊上还有一层楼

动手之前先摸清读取的地形，不然改到哪儿都是盲人摸象。

**长文本进 BookScope 有两条路，早在 exp009 就定了：不靠向量。** 一条是长上下文 + 前缀缓存——把书当成一段稳定的前缀塞进模型，同一本书的不同功能都吃这段缓存的折扣；另一条是 BM25 全文检索兜底。exp009 实测过，纯语义的向量检索只擅长"按意思找一句话"这一类活，而书籍分析真正值钱的结构关系（谁跟谁什么关系）、全局聚合（这本书的母题怎么演变）它够不着，加上禁 GPU 的硬约束，本地小模型的向量方案当时就被否了。所以 BookScope 走的是"长上下文 + 缓存 + 结构化"这条路。

值得记一笔的是：这条"书当稳定前缀吃缓存"的路，不是押在某一家 provider 的独门特性上。研究笔记 013 核实过，前缀缓存是主流 provider 的通用能力——Anthropic 缓存命中省约九成成本、OpenAI 自动缓存省约一半、DeepSeek 同样默认开自动前缀缓存。所以缓存这条 lever 是骑在一个"人人都有"的能力上，换 provider 也成立，不是"DeepSeek 有个便宜缓存我们赶紧薅"的机会主义。

**这条路上的核心构件叫脊。** chapter-13 讲透了它：几百万字的书整本精读一次，逐章产出带原文证据的结构化记录，下游十几个功能不再各自重读全文，全从这一份记录派生。书的脊叫章脉（`chapter_spine.py`）。它是整个分析的单一事实源——建对了下游秒出，建错了下游全脏。这一程要让它更快、更省 token，对象就是"章脉怎么建得更快更省"。

研究笔记 012 把章脉的学理来路也考了：**章脉本质是 ReadAgent 的 gist memory + RAPTOR 的底层摘要的合体**，方向经文献验证是当前的正路，不是土办法。ReadAgent（DeepMind，2402.09727）读一次压成要点、要证据时才回原文取；RAPTOR（Stanford，2401.18059）递归聚类摘要建多层抽象树。章脉现在是扁平的一层（只有逐章），RAPTOR 那条指向"章脉之上再聚一层卷/幕节点"——几百章聚成几十个节点，全局功能在节点层算，省的是全局分析的 token。这一层（卷层）exp021 已经 probe 过 GO、基础设施也搭了（`2e37e49`），但它是另一条 lever，这一程先不铺，只在收口时点它一句。

地形看清了：**这一程的战场就是"章脉冷建"这一格——怎么让整本读一次这件事，读得更省、建得更快，还不掉质量。**

## 三、诊断：安史那五分钟，大半不在算法上

回到那块秒表。把安史的五分钟拆开，两笔冤枉账。

**第一笔：schema 升版，全书缓存作废，这次是冷建。** 前一天（07-08）为了把人物关系抽得更深，章脉的结构版本从 v1 升到了 v2（`SPINE_SCHEMA_VERSION`）。版本一变，所有旧缓存全部失效——因为缓存的 key 里带着 schema 版本，v1 的缓存对 v2 就是不存在。所以作者这次打开安史，命中的不是缓存，是从零冷建整条 v2 章脉。这不是 bug、不是回归，是**每升一次结构版本，每本书吃一次冷启动**的既定代价。诊断的第一步就是把这条认清楚：安史这次慢，一部分是"活该慢"——它本来就在冷建。

**第二笔，才是真该修的：同一条章脉建了两遍。** 预热端点接了前端（换书就触发，后台线程默默建脊），这本是对的设计——让用户在浏览别的东西时，脊在后台悄悄建好。可问题出在：用户点开某个可视化时，那个 viz 端点直接调 `get_or_build_spine` 去拿脊，它**不看预热建到哪儿了**。冷启动那一刻缓存还空着，预热线程在建、viz 端点也 miss，两边就各自从头建同一条章脉。双份 token，双倍墙钟。这一笔是实打实的浪费——同一件事干了两遍。

诊断到这里，方向就分岔了：schema 冷建这笔改不了（evidence-first 的地板），但"建两遍"这笔是纯浪费，砍掉它零代价。这就是下一节那件干净的赢。

顺带说，这一诊断本身也是个教训：**"读安史五分钟"最容易被当成"算法慢，加并发"，但真拆开，安史这种中等书段数本来就少、并发早就跑满，加并发对它一点用没有。** 它变快几乎全在"别建两遍"上。差点顺着本能去加并发，就是没先诊断、先动手——这条后面第九节还会回来说。

## 四、一次干净的赢：单飞

砍掉"建两遍"的机制叫单飞（single-flight）：同一条章脉，并发时只让一个线程真建，其余的等它建完、再去读缓存。

实现落在 `chapter_spine_cache.py`（2026-07-09 工作区改动）。逻辑不复杂，但每一步都在防边角：

- 进程内一把锁 + 每个 key 一个 `threading.Event`。第一个来建这条 key 的线程当"领头"（leader），真去建；后来的都不是领头，就在这个 Event 上等。
- 领头建完（成功或失败）清掉登记、放行所有等待的线程，它们醒来重读缓存——读到就用，没读到自己兜底建。
- 等待带超时（`_INFLIGHT_WAIT_TIMEOUT = 900.0` 秒），够几百万字超大书冷建；就算领头线程挂了，等待方也不会永久卡死。
- 领头拿到"我来建"的资格后，还做一次双检：从"首次 miss"到"抢到领头"之间，可能有别人刚建完写了缓存，再读一次，命中就直接返、不白建。

这件事干净在哪：**它不动任何质量，纯粹是把重复的一份活删掉。** 预热和 viz 点击不再各建一遍，省一半重复 token、不再双倍墙钟。对安史这种中等书，它就是那五分钟里最大的一块——不是因为算法变快了，是因为不再干两遍。7 个新单测 + 2 个既有回归、406 个章脉/缓存相关测试零错。

单飞是这一程唯一"既快又省、零质量代价"的赢。往后三个 probe，全是想再往前走一步，然后一步一堵墙。

## 五、第一堵墙——合并分维（exp028）：input 砍半是真的，关系掉两成也是真的

第一个想法来自研究笔记 012 列的方向 A，学理来路很硬：ReadAgent 每页只 gist **一次**，而章脉现在是分人物维、情节维**两趟**扫全书——等于把整本书送进模型两遍。合并成一趟，input 理论上砍半。而且假设里还带一句诱人的："一趟同时看人物和情节，per 章更连贯，可能更好。" 又省又好，听着完美。

**先 probe，别拍脑袋。** 脚本 `scripts/probe_dim_merge.py` 在三国（73 万字 / 121 章）上冷启动跑，缓存关掉，monkeypatch 计 input/output/截断，不动产品。关键的实验设计是：两个条件用**完全相同**的 map-reduce 机器（一样的段大小、一样的纠偏、一样的兜底），只差两趟 vs 一趟。而且合并这一侧跑了两档输出预算——16000 和 32000——这一档设计是伪负例的关键，下面说。

| 指标 | 两趟 baseline | 合并 @16000 | 合并 @32000 |
|---|---|---|---|
| input tokens | 1,352,535 | 664,848（**−50.8%**）| 696,718（**−48.5%**）|
| output tokens | 233,289 | 142,959 | 147,157 |
| 截断率 | 2%（1/44）| 5%（1/20）| **0%（0/25）** |
| 关系数/章 | 9.69 | 7.47 | **7.53** |
| present/章 | 21.08 | 20.65 | 18.23 |
| 点名视角率 | 0.625 | 0.3 | **0.55** |
| 核验率 | 1.0 | 0.942 | **0.983** |

数据把假设劈成了两半，一半真、一半假。

**真的那半：input 砍半，确定无疑。** 送书一遍而非两遍，−48% 到 −51%。这是省 token 的大头——成本模型里 input 占约九成开销，砍一半 input 几乎就是砍一半钱。

**@16000 太挤，@32000 修好了一批毛病。** 这里就是那个伪负例的用处：如果只跑 @16000，看到截断 5%、视角率掉到 0.3、核验掉到 0.942，很容易归因成"合并本身不行"。但加一档 @32000 当对照，截断回到 0%、视角回到 0.55、核验回到 0.983——证明这批毛病是"输出预算不够挤出来的"，不是合并的锅。当初分两趟"怕 8000 截断"的顾虑，在 16000 下还在，32000 才够。这一档对照，把"预算问题"和"合并本身的问题"干净地分开了。

**假的那半——也是这堵墙——关系密度补不回来。** @16000 是 7.47，@32000 是 7.53，两次独立跑高度一致，都比两趟的 9.69 少约 22%。present/章 甚至更低（18.23）。加了预算、修好了截断和视角，关系密度纹丝不动地停在低位。**这就说明它不是预算问题，是"一个 prompt 同时盯人物和情节"的固有代价**——专抽人物的那一趟，会把关系挖得更深；一趟里人物和情节抢注意力，关系就抽浅了。

对着目标"token 少 + 解得更好"一量：合并给了 token 少，却让关系维**解得更浅**，而且掉的正是关系图、关系编年、人物志共用的那个公共底座。**"更好"那一半没满足，反而更差。判定 NO-GO，不改成一趟，留档。**

留档不是丢掉。将来如果只想更快、且能接受关系浅一档，或者补一版"关系专项加强"的 prompt 再 probe（n≥3），它可以复活。但当前生产不改。

## 六、第二堵墙——加并发（exp030）：瓶颈根本不是并发

合并这条 token 大 lever 被质量顶回来了，那"章脉快一倍"还有没有别的路？作者明确要"章层建得快一倍以上"，最直觉的 lever 就是并发。研究笔记 013 的调研也指着这条：Google 的 langextract（37.1k 星）默认 20 路并发抽整本小说，而我们才开 6 路；DeepSeek 官方文档写明并发无硬上限，429 才是限流信号。

**但加并发有个必须先做的前置。** langextract 的调研顺出一个隐患：现在段调用一旦出错是"跳过该段"（`exhaustive.py` 里段调用抛异常就返空列表）——这在低并发下没事，可一旦并发拉高、provider 过载返 429，就会被当普通异常直接跳过，**等于丢章**。所以先给段调用接上 429 指数重试：复用 `loop_shared.py` 里已有的常量（`DEFAULT_RATE_LIMIT_RETRY_LIMIT=3` + `RATE_LIMIT_BACKOFF_BASE_SECONDS=1.0`），过载了就等 1 秒、2 秒、4 秒再重试，让路而不是丢内容；非限流的错误仍按老行为跳过该段。这一步是把并发拉高的安全带，50 个相关测试过、零回归。

安全带系好，probe 上（`scripts/probe_concurrency_scale.py`，明朝 1.59M 字 / 158 章冷建，只改 `max_workers`）：

| 每维 workers | 总并发 | 墙钟 | 掉章 | 429 | 段调用 | input |
|---|---|---|---|---|---|---|
| 6（现状）| 12 | 401s | 0% | 0 | 89 | 2,432,690 |
| 16 | 32 | 296s | 0% | 0 | 113 | 2,706,139 |

6→16，墙钟 401s→296s，约 **1.35×**。不是两倍。

这堵墙的形状，藏在那两个 0 里：**32 并发下 429 = 0、掉章 = 0。** 意思是并发余量还很大，远没撞到 DeepSeek 的限流；可墙钟只降了 1.35×。既然不是被限流卡住，那卡住的就是别的东西——**真瓶颈是每次调用本身的延迟，加上截断恢复的串行长尾。** 每段十来万字要吐一万六的输出、还带 reasoning，单次调用就慢；碰上截断了要续抽、缺章了要补抽，这些是串行的尾巴。加 worker 只能压"能并行的那部分"，压不动"每次调用多慢"和"串行的恢复尾"。W=16 甚至多做了恢复调用（113 vs 89 段调用）却还更快，说明归一化后并发的帮助其实不止 1.35×——但够不到 2×。

前置那步倒是实打实有用：两档掉章都 0，证明 429 重试让高并发也不丢内容，前置做对了。

**判定：并发单独 NO（1.35×），够不到"快一倍"。** 但这 1.35× 是免费的——0 429、0 掉章、零质量代价，所以并发调高该做，只是它单独兑现不了"快一倍"。免费的这份照拿，生产改成 `_SPINE_DEFAULT_WORKERS = 16`（只动章脉，别的穷尽化功能仍 6 路不变，22 个测试过）。

## 七、第三堵墙——段大小（exp031）：这是个旋钮，不是杠杆

并发探完，冒出一个反直觉的猜想。既然并发余量这么大（32 并发还 0 429），那当初"段放大"（exp020，把每段放到十来万字、`454c36c`）是在"并发受限"的假设下做的最优——并发不受限了，反过来会不会**小段 + 高并发**更快？小段每次输出少、更快，还基本不撞截断、省掉那些续抽补抽的尾巴。

probe（`scripts/probe_segment_size.py`，明朝，固定 16 路，小段 40k vs 大段 120k）：

| char_budget | 墙钟 | 掉章 | 截断 | 段调用 | input |
|---|---|---|---|---|---|
| 120k（大，现状）| 295.8s | 0% | 有（触发续抽/补章）| 113 | 2,706,139 |
| 40k（小）| 333.1s | 0% | **0** | 105 | **2,212,232** |

小段对大段：墙钟慢 **1.13×**，input 省 **18%**。半对——token 赢，速度输。

**小段省 18% input 是真的、还是质量无损的省。** 小段基本不撞输出上限（截断 0），省掉了大段那些"截断→续抽/补章"的额外调用。这是白捡的 token。

**但小段更慢（+13%）。** 段小了，段数从每维十来段涨到四十来段，16 路要多跑好几波；波数增加，盖过了"每次调用更快 + 少补抽"的好处。所以小段不是加速的杠杆。

结论把 exp020 和 exp031 缝在一起：exp020 的"段放大更快"在**速度**上仍成立（大段少波数），exp031 补上的是——大段的代价是**截断恢复多花约 18% token**。所以**段大小是 token 和速度之间的一个旋钮，不是双赢的杠杆**：往大拧偏速度、往小拧偏省钱，两头够不着一起赢。中段（60-80k）大概是这个旋钮上 token 和速度更优的折衷点，但它只会落在 1.3-1.5× 这个区间、够不到 2×，先不追。现在留大段，偏速度——反正缓存已经覆盖了重复读的那部分 token，冷建这一次的 token 差没那么关键。

## 八、收口：干净的加速到 1.35× 为止，2min 不靠冷建两倍

三堵墙探完，边界就清楚了。把这一程的账摆齐：

| 手段 | 效果 | 质量代价 | 判定 |
|---|---|---|---|
| 单飞（去重复建）| 省一半重复 token + 不双倍墙钟 | 零 | **生产已改** |
| 并发 6→16 | 墙钟 ~1.35× | 零（0 429、0 掉章）| **生产已改** |
| 段大小旋钮 | 大段偏速度 / 小段省 18% token | 零，但两头不可兼得 | 留大段偏速度 |
| 合并分维（一趟）| input 砍半 | 关系密度 −22% | **NO-GO，留档** |

**质量无损的加速，封顶在约 1.35×，够不到作者要的两倍。** 干净的 2× 只剩一条路——合并两趟为一趟，直接砍一半工作量——而这条正是 exp028 那堵墙：关系掉 22%。也就是说，"章脉快一倍"这个要求，本质上被逼成了一道**拿质量换速度**的取舍题，不是工程能自己拍的。

这道题作者拍了：**不换。** 关系是关系图、关系编年、人物志的公共底座，砍它两成换来的那点冷建速度不划算。

那"任何书进 2min"怎么交代？靠第一节那个分档的诚实：**交互体感的两分钟，不靠"冷建快两倍"这单一指标去堆，靠预热 + 缓存 + 单飞。** 用户换书时预热在后台默默把脊建上，单飞保证只建一遍不浪费，建完进缓存、再开秒出。用户等的是"从点开到看见"，不是"章脉冷建的绝对秒数"。把 2min 挂在冷建速度上，就会去做那种赔质量的事；把它挂在"预热 + 缓存 + 不重复建"上，才既守住体感、又没赔掉任何东西。

至于超大书的冷建——几百万字物理上进不了 2min，这是 evidence-first 读一遍的地板，只能预热 + 提前提示，不装成 KPI。

几条没追的候选也留个账：机械抽取换更快/非 reasoning 的模型（cascade 思路，得单独 probe），段大小的中段折衷（60-80k，只在 1.3-1.5× 区间），以及那条真正双赢的结构升级——卷/幕层（exp021 已 GO、infra 已建 `2e37e49`）。卷层省的是**全局分析**的 token（几百章聚成几十个节点再算），不动逐章抽取的深度，所以它才是同时满足"token 少 + 解得更好"的正路，比合并对得多。它是下一程的事。

## 九、方法论：三个 probe 教的四件事

这一程真正的资产不是那 1.35×，是三个 probe 怎么设计的。花了不少 token 换来三个"不行/没到底"，值不值，全看方法立不立得住。四件事：

**一、先立假设 + 伪负例/对照，再动手改代码。** 三个 probe 没有一个是"改了看看快不快"。exp028 之所以能断定"关系 −22% 是固有的、不是预算问题"，靠的是同时跑 @16000 和 @32000 两档——加预算这个对照，就是伪负例：如果关系能被预算救回，那是挤出来的；救不回，才是固有的。exp030 之所以能断定"瓶颈不是并发"，靠的是同时记 429 数——32 并发下 429=0 这个对照，直接排除了"被限流卡住"的解释。exp031 之所以能干净归因，靠的是固定 workers=16、只动段大小这一个变量。**每个 probe 都先想清楚"什么数据能证伪我的假设"，再去跑。** 这跟项目一贯的发明区 probe 打法一脉相承：正例证能力、伪负例防自己骗自己。

**二、n=1 的墙钟，守方差纪律，不下精确倍数。** 三个 probe 的墙钟都是单次跑的。墙钟这东西方差大——同一条命令跑两遍能差出百分之十几。所以通篇不写"1.354×"这种假精确，只写"约 1.35×""够不到 2×"。这条是 `feedback_baseline_variance_first` 的纪律：单次数当不了 ground truth，差距要大于噪声才敢下结论。1.35× 和 2× 之间差得够远，敢说"够不到两倍"；但 1.35× 本身是个约数，不当真值。相比之下，token 和关系密度这些是确定性计数（数 token、数关系条目），两跑一致（7.47 / 7.53），才敢下 −22% 这种精确判断。**哪个数敢精确、哪个数只敢约，取决于它方差大不大，不是一刀切。**

**三、动手前先扒前人，借鉴-vs-发明两道闸。** 研究笔记 013 是这一程动代码前先做的：WebSearch + WebFetch 扫了两轮 git 高星项目（RAPTOR / LightRAG / langextract / GraphRAG / DeepSeek 文档），对着 BookScope 的硬约束（禁 GPU、evidence-first 要逐字原文、已否决 embedding、用托管 API 不自托管）逐条筛，**借原则、不借机制**。这道闸挡下了不少弯路：GraphRAG 那套"改一处触发全图重算"的重机制，正是 BookScope"schema 一升全书冷建"痛点的放大版，绝不学；LLMLingua 删 token 压缩要本地 GPU 模型、还破逐字引用，直接排除。也顺出了两个正面借鉴：langextract 默认 20 路，坐实"并发开小了（才 6 路）"；而 langextract 这种成熟库反而用**多趟**（`extraction_passes=3`）提召回，方向跟"合并成一趟"正相反——**外面的成熟工程给 exp028 的 NO-GO 投了一票**。发明之前先问一句"外面这类问题谁解得最好"，能省掉自己撞南墙的 token。

**四、evidence-first 是分层幻觉的解药，也是 token 地板的来源。** 研究笔记 012 考出一条关键的学理：文献对"分层摘要/归并"最大的顾虑，是它会**放大幻觉、出拼接不实的结果**（NexusSum、Context-Aware Hierarchical Merging 都在警告这个）。而 BookScope 每个字段钉原文 + `verify_citations` 核验，恰恰是学界公认的、治这条毛病的机制。**所以证据锚定不是价值观负担，是差异化——它让"分层"这件在别处危险的事，在 BookScope 这儿安全。** 同一条 evidence-first 还划死了 token 的地板：读都不读没法带原文证据，所以书至少读一遍，token 省不到零。这一程所有省 token 的努力，天花板就是这条地板——从 ~2-3× 压到 ~1×，压不动更少了。认清这条，就不会去做那种"少读点书省点 token"的蠢事，那等于拿命门换成本。

## 十、收尾：把边界量出来，比把速度吹上去有用

把这一程放回案例研究的脉络：chapter-13 建起了脊，这一程是把那根脊的冷建拿去过秤，看它能免费跑多快。

答案不漂亮，但诚实：**免费的加速到 1.35× 为止。** 再往前每一步都要拿别的东西换——合并拿关系密度换、小段拿速度换。作者要的那个干净的两倍，在质量无损的前提下不存在。这不是失败，是把"章脉冷建"这一格的性能边界给量出来了。量清楚边界，才知道 2min 该挂在哪儿（预热 + 缓存 + 单飞的体感），不该挂在哪儿（冷建的绝对秒数）。

这一程真正长出来的东西有三条。

**第一条，掐表和诊断是两回事。** "读安史五分钟"最容易的接法是"算法慢，加并发"，而真拆开，那五分钟大半是 schema 冷建（改不了）加建两遍（纯浪费）——安史段数少、并发早跑满，加并发对它一点用没有。先诊断再动手，省下的是往错方向砸的一堆 token。

**第二条，性能有质量边界，越过边界的"快"是拿东西换来的。** 这一程最值钱的判断不是"怎么更快"，是"哪些快是免费的、哪些快是拿关系密度买的"。把这条线画清楚，作者才能拍那道取舍题；画不清，就会稀里糊涂 ship 一个打折版的两倍速，用户还以为白赚。

**第三条，三个 NO 比一个 YES 值钱。** 这一程唯一干净的 YES 是单飞——省一半重复、零代价。剩下三个 probe 大多是 NO 或半 NO。但正是这三个诚实的结论，把"章脉能免费提到多快"这条边界钉死了，也给下一程指了真正的双赢路（卷/幕层，省全局 token、不动逐章深度）。一份把 NO-GO 写清楚、把假精确按住、把前人调研摆出来的研究笔记，比一份只报"加速了 N 倍"的宣传稿，portfolio 价值高得多——因为下一个接手的人，能从这三堵墙上直接读到"哪儿别再撞了"。
