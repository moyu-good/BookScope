## 实验目的

验证 r1-agent-loop 架构相对于五个对照组（r0-baseline、微信读书 AI、NotebookLM、ChatGPT 直通、Claude 直通）在《明朝那些事儿·第一卷·洪武大帝》上的深度问答能力是否显著更好。

衡量两个核心维度：

1. **原文引用精度**：结论是否可追溯到具体章节段落，人工核验引用是否成立。
2. **回答深度**：AI 回答是否触及问题本质，按 rubric 1-5 评分。

辅助维度：

- **Groundedness**：结论是否有原文证据支撑（不要求显式引用）。

---

## Hypothesis · 假设

- **H1**：r1 agent-loop 的原文引用精度显著高于所有五个对照组。
  - 目标：G0 > 80%；微信读书 AI 与 ChatGPT/Claude 直通预计 < 40%；r0-baseline 与 NotebookLM 居中。
- **H2**：r1 agent-loop 的回答深度 rubric 评分显著高于 r0-baseline 和微信读书 AI。
  - 目标：G0 均值 ≥ 3.5，且 G0 均值高于 G1（r0-baseline）至少 1 分。
- **H3**：r1 agent-loop 在相同问题上比直通 Claude（无书上下文）更能体现 BookScope 的核心价值——即"真的读过这本书"的效果，表现为引用可核验、结论来自文本本体、而不是从训练记忆里回忆。

## Setup · 实验设置

### 测试对象

《明朝那些事儿·第一卷·洪武大帝》

- 格式：epub（已存在于项目测试语料中）
- 选择理由：长度适中、人物与事件线清晰、公众熟悉度高、便于人工核验原文。

### 五个候选深度问题

以下问题为初稿，作者可按需调整。选题原则：覆盖人物轨迹、人物关系、主题结构、作者视角、叙事节奏五个维度，使得对照组不能靠"背百科"拿分。

#### 问题 A · 人物轨迹 + 情感弧

> 朱元璋从乞丐到皇帝的关键转折点是什么？每个转折点他的情感状态如何变化？请按章节顺序标出。

考察点：事件识别 + 情感归因 + 章节对位。

#### 问题 B · 人物关系演变

> 朱元璋和徐达、刘伯温、李善长三个人的关系在这一卷里如何演变？请引原文片段说明。

考察点：多人物关系追踪 + 原文片段引用。

#### 问题 C · 主题结构

> 这一卷的主要矛盾结构是什么？是阶级矛盾、权力博弈、个人命运、还是别的？理由。

考察点：主题抽象能力 + 证据链支撑。

#### 问题 D · 作者态度分析

> 作者当年明月对朱元璋的叙述态度是同情、批判、还是中性？举 3 个原文段落说明。

考察点：作者视角识别 + 段落级文本证据。

#### 问题 E · 叙事节奏

> 这一卷和整部《明朝那些事儿》的叙事节奏是什么关系？是开局慢热、还是紧凑铺垫？结合具体章节说明。

考察点：宏观结构判断 + 章节定位。

### 评分 Rubric

#### 原文引用精度（0–100%）

- 识别回答中每一处显式引用，例如"据原文……提到……"、"第 X 章中写道……"、"原文：『……』"等。
- 人工核验：引用是否真实存在、章节归属是否正确、片段含义是否被正确表述。
- 计算：正确引用数 / 总引用数。
- 捏造原文、错引章节、篡改段意均判为错。
- 回答中无任何显式引用时，本指标记为 N/A，但回答深度得分上限降为 3。

#### 回答深度（1–5 分）

| 分值 | 含义                                                                                           |
| ---- | ---------------------------------------------------------------------------------------------- |
| 1    | 陈词滥调，任何人不看书也能写（例：朱元璋经历了从苦难到崛起的转变）                             |
| 2    | 浅层摘要，罗列了一些具体事件但缺乏分析                                                         |
| 3    | 具体分析，指出因果关系和关键转折                                                               |
| 4    | 深度分析，叠加叙事结构、作者视角或主题层面的洞察                                               |
| 5    | 读书人级洞察：触及问题本质、发现隐藏线索，或给出该书独有、不可替换的解读                       |

#### Groundedness（0–100%）

- 回答中的每条结论是否在原文逻辑上可以找到出处。
- 不要求显式引用，但评分人需能指出该结论对应到书中的哪一处（哪一章、哪一事件）。
- 结论无法回溯到原文视为未 grounded，直接扣该条分。

## 执行流程

（整段执行流程已下放远期，2026-06-11：以下步骤是将来重启对照实验时的底稿，现阶段不执行。）

1. 等待 r1-agent-loop 首个可跑版本在 main 之外的分支落地，具备稳定运行能力。
2. 对 5 个问题分别在 6 个对照组运行一次，保存每次运行的完整原始输出（JSON 或 Markdown）。
3. 作者或可信的第三方按"双盲"方式评分：
   - 遮蔽对照组 ID。
   - 随机打乱顺序。
   - 评分人在评分前不知晓某份回答来自哪个组。
4. 按 rubric 三维度分别评分，得出每份回答的三个分值。
5. 汇总为 5 × 6 的三张分数表（精度表、深度表、Groundedness 表）并计算每组均值。
6. 产出对比表 + 关键定性案例分析（哪题哪组令人意外、哪题哪组崩盘、哪题哪组打平）。
7. 评分结束后，将关键发现沉淀到 `docs/internal/case-study/` 的首章，作为 r1 代际对外交付的证据。

## 失败模式预判

实验前需要对以下可能的失败模式做预案，避免中途被打断。

### 1. 超长章节 context overflow

- 问题：r1 agent 面对 5 万字以上章节可能超出上下文窗口。
- 预案：
  - 确认 r1 的 retrieval tool 已经做了章节级切分与摘要；
  - 若 agent 仍超限，人工切为上下两段分别提问，合并答案（需在评分笔记中注明）。

### 2. 微信读书 AI 不允许复制

- 问题：App 内 AI 回答常不允许选择与复制。
- 预案：
  - 手工抄录全文，双人核对；
  - 同时保存截图作为原始凭证；
  - 若遇到改写后的二次输出，以截图为准。

### 3. ChatGPT/Claude 直通组泄漏训练记忆

- 问题：《明朝那些事儿》极可能在 GPT-4o 与 Claude 训练数据中，模型可能凭记忆作答。
- 预案：
  - 在系统提示中明确禁止调用训练记忆（见 Setup · 公平性约束）；
  - 评分时若发现回答内容与原文无关、但符合公众认知，判为未 grounded；
  - 额外保留一行"怀疑来自训练记忆"的标注，便于后续讨论。

### 4. 评分主观性差异

- 问题：同一份回答，不同评分人可能给出不同分数。
- 预案：
  - 先做 1–2 题的 pilot 双评；
  - 计算 pilot 段的评分一致性（简单做法：差 1 分以内视为一致）；
  - 若一致性差，回来统一 rubric 理解，再开始主体评分。

### 5. 对照组版本漂移

- 问题：微信读书 AI、NotebookLM、ChatGPT、Claude 的底层模型在实验周期中可能静默升级。
- 预案：
  - 在每份输出中同时记录调用时间与可见的模型版本标识；
  - 评分笔记中如发现行为差异，特别备注。

### 6. 选题偏向 r1

- 问题：五个问题均偏向结构化/引用类任务，可能对 r1 有利，对直通组不公平。
- 预案：
  - 实验报告中显式承认这一偏向；
  - 后续实验 002 起考虑增加开放性 / 主观性题目做补充。

## Pilot 观测 · 2026-04-24（非正式首跑）

r1 首次拿到真 API（讯飞星辰 `astron-code-latest`，OpenAI 兼容）端到端跑通的第一个观测，**不属于正式实验设计的任一轮**，仅作为"链路能通"与"基线耗时"的 pilot 数据记录。

### 配置

- Provider：astron（通过 `DeepSeekAdapter` + 自定义 base_url `https://maas-coding-api.cn-huabei-1.xf-yun.com/v2`）
- Model：`astron-code-latest`
- 书：`test明朝那些事儿.epub`（32164 字 / 1069 chunk）
- KG：smoke test 脚本手工造的 4 角色（朱元璋 / 李善长 / 徐达 / 常遇春），章节索引 regex+schema 双路径
- Embedding：未启用（BM25-only，`SessionVectorStore(enable_vector=False)`）
- Rerank：**已熔断**（`r0_search_chunks.py` 显式 `enable_rerank=False`，见 ADR-006）
- 问题：`这本书里主要有哪几个角色？`

### 结果

- 总耗时 **82.3 秒**（4 iterations / 6 tool 调用）
- Tool 分解：`search_chunks` 2 次（6ms + 11ms）+ `list_characters_in_chapter` 4 次（每次 0ms）
- Token：input 56,827 / output 1,291
- Outcome：`success`
- Answer：按时期梳理出 50+ 角色（洪武→永乐→土木堡→弘治→嘉靖→万历→崇祯七段）
- Citations：7 条（chapter 1 目录 + chapter 24/39/98/100/106/145 原文 snippet）

### 观察与已记录的裂缝

1. **Answer 密度 > Citation 密度**：answer 列 50+ 角色但仅 7 条 citation——多数角色名来自 chapter 1 的书目 snippet 与其他章节 snippet 的组合推理，未逐个 citation。与 H1 目标 G0 > 80% 的引用精度要求不吻合，需在正式实验中复测
2. **`list_characters_in_chapter` 贡献为零**：smoke KG 只 4 角色，agent 4 次调用全返回同 4 个人；answer 的丰富性实际全靠 `search_chunks`。**正式实验必须先跑 `MinimalKGExtractor`**，不然这个 tool 形同虚设
3. **Reranker 必须下线**（→ ADR-006）：cross-encoder 本地推理在 1069 chunk 上一次 search 耗 200-400 秒，违反"禁止 GPU"+"10 秒读取"两条硬约束
4. **首次真实验暴露的前置修复**：
   - smoke test `sorted({None, int, ...})` bug
   - `LoopTimeout` / `MaxIterationsExceeded` / `ToolDispatchError` 原先丢失 trace，已改为异常带 `.trace` 属性
   - astron 单次 tool-use 调用未见异常慢（第三轮 trace 显示模型推理只占少量时间，tool 本地执行才是 bottleneck）

### 这次 pilot 不等于实验 001 G0

正式实验 001 的 G0 轮必须满足：

- 全 5 题（本 pilot 只 1 题）
- `MinimalKGExtractor` 跑完产出真 KG
- 三人盲评 rubric + 引用精度
- 至少重复 3 轮（本 pilot 仅 1 次）

本 pilot 的价值是：**证明 r1 端到端链路在真 API 上可通、耗时可控**（82s 远低于曾经担忧的"外部 provider 导致查询分钟级"预期），为正式实验铺平道路。

## Pilot 观测（二）· 2026-04-24 · 20-chunk 真 KG 抽取

第 22 轮执行。第 18 轮给 smoke test 接入了 `MinimalKGExtractor` 的 opt-in 路径，本轮是它**首次被真跑**，用最小成本配置验证路径通、质量基线、trace 可信度。

### 配置差异（vs pilot 一）

| 项 | pilot 一（第 16 轮） | pilot 二（第 22 轮） |
|---|---|---|
| KG 来源 | smoke 脚本手工列 4 角色（朱元璋/李善长/徐达/常遇春） | `MinimalKGExtractor` 真抽取 |
| KG 输入 chunk 数 | — | 前 20 / 1069（`BOOKSCOPE_SMOKE_KG_CHUNK_LIMIT=20`，约覆盖书的前 2%） |
| KG 抽取耗时 | 0（手工即时） | 46.0s（1 次 LLM batch） |
| Extractor 产出角色数 | — | **32**（前 20 chunk 合并去重后） |
| 其它 | 同 pilot 一（astron / BM25-only / rerank 已下线） | |

### 结果

- Agent query 耗时 **62.7s**（pilot 一 82.3s；差异主要来自 astron 网络波动与 agent 迭代次数相同 4 iterations）
- Citation **10 条**（pilot 一 7 条），覆盖章节从 `{1, 24, 39, 98, 100, 106, 145}` 扩展到 `{1, 2, 9, 10, 24, 98, 106, 128, 140, 145}`——多命中 chapter 2（朱元璋履历）/ 9（常遇春）/ 10（陈友谅）/ 128/140（魏忠贤/崇祯）等精准原文
- Total token 67,690 input / 1,377 output（pilot 一 56,827 / 1,291）
- Answer 结构与 pilot 一类似（时期分段 + 代表人物），但个别判断更细致（例如本轮答案单独提到刘基 / 朱允炆 / 汉王朱高煦 / 解缙 / 杨溥等 pilot 一漏掉的名字，这些应该是多抓的原文 snippet 推理出来的）

### `list_characters_in_chapter` 的行为对比（诊断价值高）

| 调用 | pilot 一（手工 KG） | pilot 二（真 KG，前 20 chunk） |
|---|---|---|
| `chapter=1` | list[4]（固定 4 人） | list[3]（真抽到的 chapter 1 角色） |
| `chapter=50` | list[4]（**误报**：手工 KG 把 4 人的 `key_chapter_indices` 填满所有章节，agent 被告知"这些人也出现在第 50 章"） | list[0]（**诚实**：KG 只覆盖前 20 chunk，第 50 章确实没抽到人） |
| `chapter=100` | list[4]（误报同上） | list[0]（诚实） |
| `chapter=150` | list[4]（误报同上） | list[0]（诚实） |

**关键观察**：pilot 二的 `list[0]` 比 pilot 一的 `list[4]` 更可信。agent 的探查策略（试探性跨章跳查）在真 KG 下会**诚实地"未命中"**；手工 KG 反而在这里欺骗了 agent。这个对比侧面验证 `MinimalKGExtractor` 的输出可信度——它会**老实说"我没看过这里"**，而不是每章都给同一份 mock。

### 给正式 G0 的启示

1. **extractor 路径工程上通**（62.7s 全链路 / 32 角色产出 / trace 可观测性齐全）—— 第 18 轮承诺闭合
2. **KG 覆盖率直接决定 `list_characters_in_chapter` tool 的可用性**。前 20 chunk 只覆盖书的前 2%，所以"正式实验必须先跑完整 KG"这条硬性前置仍成立（粗估 30 分钟 / ~300 万 input token / 1069÷60≈18 batch）
2.1. **agent 在 KG 稀疏时会"盲打"跨章探查**：pilot 二里 agent 跳章试探 chapter 50/100/150 都落空，这暗示 prompt 里可以补充"KG 覆盖范围"元信息让 agent 少做无效探查——**但这是未来 ADR 级的 prompt 工程，不在本 pilot 范围**
3. **Citation 绝对数量仍未到 H1 目标 G0 > 80%**（10/50+ ≈ 20% 角色被 citation 支撑）。真全量 KG 后是否能显著改善，是正式实验必测项之一

### 撤回第 1 章草稿的一处陈述

`docs/internal/case-study/chapter-01-r1-launch-and-api-first-pivot.md` 第 7 节结尾说"副管理不主动跑真 smoke——extractor 已有单测覆盖，集成路径编译通过即可"。这条陈述截至第 20 轮成立，截至第 22 轮**已被本 pilot 覆盖**：作者"继续"指令 + key 仍在 session env 时，副管理确实主动跑了一次轻量验证。作者定稿第 1 章时可视情况补一句"第 22 轮补跑了 20-chunk pilot 验证路径，见 experiment 001 pilot 二"。
