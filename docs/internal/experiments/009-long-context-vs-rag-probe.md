# exp-009 · 长上下文 vs RAG 可行性 probe（设计）

> **性质：probe 设计草稿，待作者审。批准 + key 到位后才跑。**

**日期**：2026-06-12
**上游**：`research-notes/003`（检索范式调研，结论"长上下文+缓存"是更优方向）+ ROADMAP 地基「长上下文+缓存 probe」+ 作者定的 ≥90% 缓存硬目标
**方法论锚**：戴明·先量后改（别假设长上下文赢，对照实测）+ 项目「对照实验」usecase（同一组问题、长上下文 arm vs RAG arm、控制变量）

---

## 1. 目的

- **Why**：验"把整本书塞进 context 直接读（长上下文）+ 前缀缓存复用"是不是比当前 RAG 更适合书籍深度分析——尤其**全局/关系问题**（RAG 检索本就捞不到对的段），同时撞 ≥90% 缓存目标。
- **受益者**：深读一本书问多遍的用户（BookScope 核心场景）+ 降本目标。
- **成功标准（go/no-go）**：能塞下的书上——
  1. **质量**：全局/关系题答得对（RAG 答不上的它能答），事实/改述题不退；引用真在原文。
  2. **不 lost-in-the-middle**：答案没因为关键信息在书中段而漏（专设几道答案在中段的题测）。
  3. **缓存率 ≥90%**（第 2 问起，书是稳定前缀）。
  4. **单问成本**（首问后）≤ 当前 RAG。
  5. 延迟可接受。

质量是真正的未知（缓存/成本预判几乎必赢，见下）。

## 2. 数量级预判（确认值得跑）

anshi ~38 万字 ≈ ~30 万 token，远在 flash 1M context 内。首问全书进 context ≈ $0.04（30万 token × miss $0.14/M）；第 2 问起书命中缓存按 1/50 → 每问 ≈ $0.001 + 小问题。**第 2 问起缓存率天然 ~99%**。10 题总成本 ~$0.05。所以缓存+成本几乎必赢——probe 的重心是**质量**。

## 3. 方案概要

1. **选能塞下的书**：anshi（《安史之乱》~38 万字）。kuicheng（680 万字）塞不下，排除（那本退回检索，不在本 probe）。
2. **题集 ~10 题，混合、重点压 RAG 弱项**：
   - 全局/聚合（RAG 弱）：全书核心论点链、整体结构、主题。
   - 关系/多跳：跨章人物/事件关联。
   - 语义改述：从 golden set 取 BM25 失败的几道。
   - 关键信息在书中段的题：专测 lost-in-the-middle。
   - 2-3 道事实题作对照锚。
   - 复用 exp004 anshi 题 + 补全局/关系题。
3. **两个 arm，同题**：
   - **A 长上下文**：anshi 全文进 system 固定段（稳定前缀保缓存），问题进 user 末尾，flash 直接答 + 要原文引用。
   - **B 当前 RAG**：走现有 agent loop（BM25 检索）。
4. **测**：① 质量 head-to-head（A vs B：全局题 RAG 答不上 A 能否答、引用真实性、改述题命中、中段题有没有漏）② 缓存命中率（A 第 2..N 问的 `prompt_cache_hit_tokens`）③ 单问成本（A 首问全价 + 后续命中 vs B 每问 miss）④ 延迟。
5. **配置**：flash、DeepSeek key 从 `.env`、BookScope L2 关（A 多问要真命中 DeepSeek 服务端缓存，关 L2 避免假命中污染）。每题判质量人工 + 可核验信号为主（不靠已降级的 reviewer）。

## 4. 影响范围（批准后才动）

- 新增 `scripts/probe_long_context.py`（A arm：全书进 context 问答 + 测缓存/成本/延迟；B arm 复用现有 agent loop / run_batch 同题对照）。
- **不动生产代码**（probe only）。
- 复用 anshi epub + golden set / exp004 anshi 题。

## 5. 不做

- 不测塞不下的书（kuicheng 680 万字）——那本退回检索，超出本 probe。
- 不改生产（probe 验证后才设计接入路由）。
- 不上 pro（flash 支持 1M context，够；pro 贵 12x）。

## 6. 验证方法

go/no-go 五条（§1 成功标准）。过线 → 「长上下文+缓存」进设计开发（按书大小路由：塞得下走它、塞不下退 RAG）。不过线 → 记录根因（lost-in-the-middle？质量不如 RAG？），RAG 维持，长上下文搁置。负结果也写进案例研究。

## 7. 实跑结果与判定

**跑于** 2026-06-12，anshi（394761 字 ≈ 265K token），flash，7 题（q1-q5 全书结构题 + a1/a2 事实锚）。数据 `exp009-long-context-vs-rag-anshi.json`。

### 客观指标（长上下文压倒性）

| 指标 | A 长上下文 | B RAG |
|---|---|---|
| 缓存命中率（第 2 问起）| **100.0%**（整本 265K 全程命中）| ~50-60%（部分）|
| 总成本（7 题）| **$0.045** | $0.099（2.2x）|
| 平均延迟 | **22.9s** | 52.3s（2.3x）|
| 截断 | 无（finish=stop）| —— |

≥90% 缓存硬目标 → 打穿到 100%。边际每问 A ~$0.001 vs B ~$0.014，越问差距越大。

### 质量 head-to-head

- **全局/结构题（q1-q5，RAG 弱项、probe 重心）**：A 平手到更好。A 看得见全书——q1 给逐章节奏表（覆盖全部章节）、q5 找出"立场最弱章节 + 郭子仪未祛魅"的细微漂移——比 B（从检索片段综合、覆盖章少、q5 一口咬定无漂移）更全更挑剔。**无 lost-in-the-middle**（A 逐章表覆盖中段）。
- **事实锚（a1/a2）**：B 略全（a2 列全被杀诸人，A 只答杨贵妃）。A 不输（都对），RAG 检索 surface 出更多周边细节。

### 判定：GO（限能塞下的书）

长上下文+缓存在能塞下的书上：全局题质量 ≥ RAG、客观指标（缓存/成本/延迟）压倒性赢、无 lost-in-the-middle。

### 诚实 caveat（进开发设计要解决）

1. **只限能塞下的书**（anshi 265K 塞得下；680 万字塞不下 → 退回 RAG）。
2. **A 的全书断言要补 citation 校验**——A 自信给逐章细节但没有 chunk 级引用核验；evidence-first 不能丢（A/B 对灵宝之战给了不同章号 → 章号漂移老问题，A 逐章断言越多出错面越大）。
3. 单书单跑，signal 强，进生产前在更多能塞下的书上复跑。

### 第 2 本复跑确认（zhinei，理论书，验跨题材）

2026-06-12 在 zhinei（《制内市场》47 万字 ≈ 219K token，理论书，跟 anshi 历史书不同类型）复跑 7 题（3 全书结构 + 4 golden 真题），数据 `exp009-long-context-vs-rag-zhinei.json`：客观指标全 hold——第 2 问起缓存 **100.0%**、成本 $0.036 vs RAG $0.049、延迟 12.6s vs 39.7s（3x）、全 finish=stop 无截断、答案 substantive。**跨题材（历史 → 理论）长上下文路稳**（质量未再逐条 head-to-head 判，本轮重点验机制 hold）。caveat #3 部分消（已 2 本 2 类型；接入前可再扩，不阻塞灰度）。
