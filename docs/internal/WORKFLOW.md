## 一、项目目的（写在最前）

三个目的按优先级排列，互为支撑，缺一不可。

- **目的一**：服务作者本人作为长篇网络小说创作者的第一读者工具。最终形态是一个可以陪伴作者自审自校的工具——看出角色在某章走样、伏笔在某处失落、节奏在某段失控、世界观在某处自相矛盾。网络小说动辄几十万至数百万字，这种规模下人脑短时记忆早已不堪重负，AI 恰好可以承担这份外部记忆与交叉比对工作。

- **目的二**：在 AI 时代重新定义"书籍深度分析"。具体是构建一套以**查询时智能代理**为核心、以**原文证据**为根基、以**长篇叙事**为主要对象的分析系统，让 AI 真正"读懂"一本书，而不只是回答关于这本书的问题。

- **目的三**：沉淀一份带完整研究轨迹、工程实验数据、架构代际演进记录的**案例研究文档**（`docs/internal/case-study/`）。这份文档是本项目最终的对外产出，其价值在未来支撑 AI 产品经理、数字化咨询、独立研究工程师等方向时，高于任何星标数或用户数。

三个目的互为支撑：目的一提供真实需求与一手使用反馈，目的二提供技术深度与方法论，目的三把前两者的轨迹固化为对外可展示的资产。缺失任何一个，项目都会失去长期价值。

## 二、方向

- **技术方向**：从"批量预处理 + 静态展示"架构（r0），转向"轻量索引 + 查询时智能代理"架构（r1）。离线只做索引层，分析推理全部放到查询时由智能代理现场完成，每一句结论必须带原文引用。

- **对象方向**：当前阶段以《明朝那些事儿》作为能力测试基线；长期主要对象是作者本人正在创作的长篇网络小说。测试基线用于校准精度与召回，真实对象用于验证工具能否嵌入实际创作流程。

- **研究方向**：实践驱动、问题触发研究。论文是遇到真难题时的弹药库，不是项目的起点。先在工程层穷举已知方案，遇到真问题再回到研究层。

- **产品方向（远期参考）**：专业创作者工具 + 开源方法论库双层组合。前台变现、后台建技术信誉。但当前阶段不讨论产品化落地，专注把能力打透。

- **交付方向**：长期唯一交付物是 `docs/internal/case-study/` 持续打磨的案例研究文档。代码只是案例研究的附属证据。任何不能沉淀进案例研究的工作，原则上都可以延后。

## 三、工作原则（五条）

1. **自试优先**：作者必须本人使用 BookScope 读书与审稿。作者的自试不可由 AI 代做，每周至少 30 分钟到 1 小时。自试笔记是地面真相，一切分析能力的评判以自试体感为准。

2. **原文证据为本**：任何分析结论必须带可追溯的原文引用。没有原文支撑的结论一律视为不可采信，无论看起来多漂亮。

3. **架构代际 ≠ 提交版本号**：用 r0、r1、r2 标记架构代际，代际是思想层面的重大转变；commit 用 conventional commits 格式，是工程层面的日常迭代。两者严格分开，不混用。

4. **穷举已知方案后再看论文**：工程层优先，研究层后发。问题先在工程层试 3 到 5 个已知方案，都无法解决再升级到二层走论文汲取流程。

5. **一切痕迹可检索**：日常构建、自试、研究、实验、架构决定全部留文档痕迹，统一落到 `docs/` 下的对应目录。口头讨论不算数，未落盘的决策不存在。

## 四、日常工作方法：与 Claude 的协同节奏（CEO + AI 团队模式）

**核心认知**：项目采用"CEO + AI 团队"模式。作者是 CEO，负责方向把控加上几件不可替代的事。Claude Code 及其代理团队是 AI 执行团队，24/7 连续循环推进项目。

### 作者每周必做的不可替代事项（底线，不可删）

- **作者视角自试**：每周至少 30 分钟到 1 小时，用 BookScope 读一段书或审一段网文草稿，笔记入 `docs/internal/dogfood-notes/`
- **方向复核**：每月一次 30 分钟到 1 小时，读 AI 写的月度复盘和案例研究增量，判断 BookScope 走向
- **架构代际决策签字**：代际升级的架构决策记录末尾由作者亲手批准
- **案例研究定稿**：AI 写初稿，作者改核心叙事至少一半篇幅

### AI 执行团队每日自主节奏

- 主循环每 30 分钟一轮
- 每一轮：读取核心文件（CLAUDE.md → NORTH_STAR.md → FLAGS.md → STATE.md → 任务队列）→ 决策本轮任务 → 执行 → 更新 STATE.md
- 每日自动生成 `docs/internal/build-log/YYYY-MM-DD.md`
- 24/7 连续运行，无时间窗口限制，直到作者明确说"停"或触发红色告警

### 副管理模式的操作化

"窗口持续运行"本质上等于主 Claude 持续处于副管理姿态。落地操作如下：

- **窗口开启 = 副管理上线**。作者打开 Claude Code 窗口后，主 Claude 自动进入副管理模式，不需要额外命令触发。
- **口头"开始"即批准**。作者在窗口内说"开始 r1"、"继续推进"、"今天这块你自己安排"等高层指令后，副管理立即按指令拆解任务并推进，不等电子签名。
- **小事自动做，不请示**。命名、测试用例、rubric 子项权重、commit 措辞、依赖 patch 升级、日志格式等属于 auto-accept 范围，副管理直接执行，完整清单见 `docs/internal/DEPUTY_MANAGER.md` 第二节。
- **每轮产出后自动推进下一步**。每完成一个大步骤，副管理更新 `docs/internal/STATE.md` 并按第六节格式输出一段简短汇报，然后不等作者回复直接进入下一个大步骤。
- **只在 escalation trigger 时停**。代际升级、NORTH_STAR 改动、破坏性 git 操作、对外发布、红色告警 override、作者明确要求请示的 topic 一律停下，在汇报里写明"需要作者决定 X"。完整触发清单见 `docs/internal/DEPUTY_MANAGER.md` 第三节。
- **无事可做时不空转**。任务队列空且无告警时，副管理把观察与建议写入 `docs/internal/STATE.md` 的"副管理建议"章节，停下等指令，不编造工作。

副管理的职责边界与汇报格式以 `docs/internal/DEPUTY_MANAGER.md` 为准，本节仅作日常工作手册中的操作索引。

### 作者给问题点 → 标准处理流程（列清单 → 记录在册 → 一一解决）

作者实测后常一次甩多个问题点（多带截图 / 实例）。**每个问题点都要走完整闭环，不许有的建任务、有的随手做就忘了登记**（2026-06-30 作者明示：要列清单、记在册、一个个解决到关闭，并把这套流程记牢）。五步：

1. **列清单**：当场把每个问题点拆成独立一条，一条一个问题，不合并糊弄。
2. **溯源诊断**：逐条刨根，先看是不是通用根因而非个案（守 `feedback_global_not_single_case`）。是 bug 找错误类别、是设计问题给 take。
3. **记录在册**：每条 `TaskCreate` 进任务清单（任务清单就是"册"）；严重 / 跨功能的同时进 `ROADMAP.md` 带验收标准。**先登记再动手**，不许跳过登记直接做（哪怕是随手能改的小修，也先建一条任务）。
4. **一一解决**：小修直接做、大件走 design-first；解决一条就 `TaskUpdate` 标 completed，全程可追踪、不丢。
5. **收口汇报**：哪些已解、哪些在做、哪些 design-first 待作者批，一次说清，对得上任务清单。

判据：作者问"那个问题解决了吗"，应能在任务清单里一条条指出状态，而不是靠回忆。关联 memory `feedback_issue_intake_workflow`（这条流程的出处与细节）。

## 六、问题分级：零层、一层、二层

- **零层（日常 80% 时间）**：构建与自试。写代码、修缺陷、用工具读书、补文档。
- **一层（遇到小到中等难点）**：工程层穷举已知方案，1 天内验证。试 3 到 5 个成熟方案，挑合适的落地。
- **二层（真难题）**：升到研究层，论文汲取。穷举工程方案后仍无解，问题本身处于领域前沿。

### 示例对照表

| 示例 | 分级 | 判据 |
|---|---|---|
| 某次 LLM 调用超时 | 一层 | 已知方案充足（重试、超时参数、切分上下文） |
| 智能代理 50 轮后陷入死循环 | 二层 | 代理终止判据是领域前沿 |
| Pydantic 校验报错 | 一层 | 文档可查、边界清晰 |
| 原文引用精度在 30 万字以上降到 40% | 二层 | 长上下文归因是领域前沿 |

判错层级的代价很高：把一层问题升到二层会浪费研究预算；把二层问题压在一层会反复徒劳试错。每周反思时重点复盘分级误判。

## 七、二层研究的论文汲取五步法

1. **问题重述**：用学术术语重写难点，逼自己跳出工程表述
2. **关键词生成**：3 至 5 个检索词
3. **论文检索**：Semantic Scholar + arxiv + Google Scholar
4. **筛选精读**：前 3 至 5 篇，只记方法核心与对 BookScope 的启示
5. **回到工程层验证**：48 小时内跑验证实验

### 笔记强制字段格式

```
论文：<标题>（引用数：N，年份：YYYY）
所解问题：<一句话>
方法本质：<两到三句>
与 BookScope 的关联：<具体在哪个难点上适用>
拟尝试：<下次工程层要跑的具体实验>
实验日期：<日期>
实验结果：<一句话结论>
```

最后三行是强制字段。缺失后三行的研究笔记视为未完成，不计入研究档案。

## 十一、长期挑战与防线

1. **问题分层早期必定误判** → 每周反思诚实复盘，逐步校准升层直觉

3. **论文读完即用最难** → 研究笔记强制"实验日期、实验结果"字段
4. **方向漂移是最大敌人** → `NORTH_STAR.md` 月更 + 案例研究持续积累
5. **为研究范式牺牲自试** → 自试永远是地面真相，研究范式再精妙也不能取代作者本人的使用体感

## 十二、Claude Code 全自动协作配置（24/7 CEO 模式）

### 循环算法的位置

主循环算法、任务队列结构、escalation 触发表、失败重试矩阵、commit 节点、跨 session 续跑节奏，全部在 `docs/internal/AUTOLOOP.md`。本节只列高层边界。

### 自动化边界（高层概括）

可全自动的事：

- 代码格式化、静态检查、测试运行
- 本地 commit（按 CLAUDE.md 四要素格式）
- 论文检索摘要初稿
- 多代理并行调度
- 日 / 周 / 月报初稿
- 长耗时任务后台执行
- prompt 迭代、batch 实验、ADR 起草、case-study 章节**草稿**

必须停下等人的事，按 `docs/internal/AUTOLOOP.md` 第五节分三类：

- **物料类**：作家私稿、5 道作家题、自试笔记
- **签字类**：NORTH_STAR 修订、代际升级 ADR、case-study 章节定稿、FLAGS 告警条件本身
- **风险类**：远程 push、`--force`、分支删除、历史改写、PR / release / tag、对外发布

### 红色告警条件（写入 FLAGS.md 后 AI 立刻停该方向）

- 任何测试覆盖率下降超过 10 个百分点
- 方向 30 天未与 `NORTH_STAR.md` 对齐
- 作者手动写入 `FLAGS.md` 的条目

**成本不设红线**：作者明确 BookScope 不计较 LLM 成本，追求高效稳定的开发。AI 为保证质量可选用最强模型（Claude Sonnet / Opus / DeepSeek-R1 / GLM-4 级），无需为省钱降级。

> ⚠️ 此条已过时、与硬规矩冲突，见本文件顶部注记。现状以 `bookscope-dev-sensibility` 为准：默认 DeepSeek 最便宜档（`deepseek-v4-flash`）、禁 GPU。

### 自动化反向风险与防线

1. **自动化成为逃避思考的借口** → 初稿不等于定稿，每份必须作者至少改一半
2. **自动化让自试仪式偷懒** → 自试坚决由人类完成
3. **钩子过度致开发体验降级** → 钩子只跑轻量任务
4. **定时任务堆成噪音** → 上限 6 条，每季审查
5. **预授权清单膨胀** → 每月审查，破坏性操作踢出
